# Shell commands

The interactive shell runs on the serial console and the screen, and every
command also works over the [UDP remote shell](udp-shell.md). Trace output is
suppressed while the shell is active (it still lands in `dmesg`).

| Command | Description |
|---------|-------------|
| `cls` | Clear screen |
| `cpu` | Dump CPU state |
| `lscpu` | Identify the CPU and report the features the kernel depends on (1 GiB pages, NX, PAT, invariant TSC, ARAT), the performance counters it has (Intel architectural perfmon, or AMD core counters and PerfMonV2), and which of them `profile` will actually sample with |
| `dmesg [lines] [filter]` | Dump kernel log: newest `lines` messages (all of it if omitted), optional substring filter |
| `loglevel [N]` | Show or set the trace level (0-5) on a running kernel |
| `uptime` | Show uptime |
| `date` | Show wall clock date and time (RTC + boot time) |
| `igbdump` | The igb chip's own state: MAC command/status registers, ring head and tail, receive statistics; the interrupt layout (INTx, one MSI-X vector, or a queue vector and another) with each vector's count, the throttle and the receive rate it follows, and how often under load the poll looked at an empty ring again rather than arm the interrupt, with the time that cost; and the PHY's view of the link — what it advertised, what the partner offered, both 1000BASE-T registers. What made the I210's 10 Mb/s latch diagnosable |
| `nicdump` | The r8125's own state: command register (is the receiver still enabled?), interrupt status and mask, and whose the head receive descriptor is. For a machine that has stopped receiving and can still be typed at |
| `stacks` | Stack high-water marks: every stack is filled with a pattern when it is created, and what is still intact is what it never reached. Catches a spike that lasted microseconds during boot, and costs nothing while the machine runs |
| `ps` | Show tasks |
| `top [ms]` | Per-task CPU use over a sampling window, percent per CPU (a busy thread reads 100%, a 20-CPU box tops out at 2000%), plus the number of tasks moved between CPU queues since boot, and of reschedules deferred because the task they landed on had preemption off, in the window and since boot -- how many of those on an idle task |
| `sched [ms]` | What each CPU's scheduler did over a window (a second unless given), a line a CPU and one for all: how many tasks are on its queue; how many were woken and how long they waited for the CPU -- the median, the 99th and the 99.9th percentile as the bounds of the log2 buckets they fell in, and the longest since boot exactly; how many were displaced while they could still run, and how long until they ran again; how many decisions it made, what one cost on average in the window and at most since boot, and how many tasks each touched; how many tasks could run each time the CPU's timer had the queue looked at -- on average, the most since boot, and how often two or more. See [Scheduler](scheduler.md#what-it-is-measured-by) |
| `sched probe [spinners=2] [ms=2000] [cpu=N]` | How long a woken task waits for a CPU that others keep busy: `spinners` tasks that never yield, pinned to `cpu` (the highest one other than the shell's, unless given), a waiter pinned beside them asleep on an event, and the shell's task signalling it from its own CPU a sample at a time; the waits from each signal to the waiter running, as percentiles and the longest, the signals not answered within a second, the lag the waiter woke with -- least, average and most, in virtual microseconds -- and the share of the window each task ran. See [Scheduler](scheduler.md#a-woken-task-behind-spinners) |
| `sched queue [cpu]` | What EEVDF has of each task a CPU (this one unless given) can run, the one on the CPU first and starred: pid, nice, slice in microseconds, lag and deadline in virtual microseconds from V, whether it is eligible, and its name. See [Scheduler](scheduler.md#who-runs-next-eevdf) |
| `sched nice <pid> <-20..19>` | A task's nice: its weight, and so its share of its CPU beside others that want it -- each step about ten per cent between two tasks |
| `sched slice <pid> <100..100000>` | A task's slice in microseconds: how long it runs at a time, and so how soon after it is eligible it runs -- a short one is lower latency, not a larger share |
| `profile [ms] [pid\|all] [chains]` | Sampling profiler: where the kernel spends its time, as whole call chains -- samples are folded by their entire stack, not by the leaf symbol, and the hottest chains are printed in full. `chains` caps how many, for a console with no scrollback -- `profile 2000 all 3` fits a screen where the default does not. Every frame carries its offset: the leaf as the instruction the sample landed on (a span when they spread across the body, so a hot spinlock says whether it sat on the exchange or in the pause loop), each caller as the return address that names which call site led there. Samples on a performance counter overflowing into an NMI (~1 kHz, and catches code running with interrupts off) where the CPU has one -- Intel's architectural fixed counter 1, or AMD's PMCx076 on family 15h and later, both counting unhalted core cycles; falls back to the 100 Hz per-CPU tick where it does not, which includes any machine whose hypervisor answers CPUID for a PMU it declines to virtualise (the counter is asked to prove it counts before the profiler trusts it). The report names which |
| `bt <pid>` | Where a task is -- blocked, asleep, runnable, running on cpu N at a function, or on a CPU that took no interrupt in a second -- and its stack trace ([Scheduler](scheduler.md#waiting-for-one-to-end)) |
| `watchdog` | Watchdog stats: locks watched, table walks, and the slice of the bucket table each CPU walks (the table is divided among the CPUs, so a bucket is visited once per tick rather than once per tick per CPU) |
| `memusage` | Show memory usage: free and total pages, and the huge pool's free and total 2 MiB blocks (`hugepages=`) |
| `meminfo` | Show the firmware memory map, and how much of it the kernel actually uses |
| `memcheck` | Verify no reserved, kernel-image or absent page reached the free list |
| `pci` | Show PCI devices |
| `disks` | List block devices |
| `diskread <disk> <sector>` | Read and hex-dump a sector |
| `diskwrite <disk> <sector> <hex>` | Write hex data to a sector. Refused on a device a mounted filesystem, the disk log or a `blkload` write test holds, or on a disk or partition overlapping one (see [Filesystems](filesystems.md)) |
| `partitions <disk>` | Show the partition table (MBR or GPT) |
| `disklog` | Kernel-log-to-disk state: off unless the kernel was booted with `disklog=on`; otherwise the prepared area it found (if any), boot number, sectors written, lines queued and dropped. The area is laid down under the host OS with `scripts/disklog.py format` and read back with `scripts/disklog.py read` |
| `irqstat` | Show per-device interrupt counters |
| `help` | List commands |
| `net` | List network devices and per-protocol stats |
| `arp` | Show ARP table |
| `nat` / `nat allow <a.b.c.d[/n]>` / `nat deny <a.b.c.d[/n]>` | Whether NAT is on, between which devices and from which address; the first mappings, each with its protocol, the guest's side, where it goes, the external port it has and how long it has left; where the guests are kept from -- link-local (a cloud's metadata server), the private networks, the shared space, the uplink's own subnet -- and what `nat allow` let through of it; and what NAT has done -- packets out and back, mappings made and those made by taking the least lately used flow of the guest holding the most (a full table), and the packets it had no room, next hop or frame for, does not take, or denied. `allow` lets the guests reach a network the deny list keeps them from, up to 16, and `deny` takes that back. The hypervisor's switch turns it on for its guests. See [The way out](hypervisor.md#the-way-out-nat-dhcp-and-dns) |
| `netpool` | Show the recycled net frame pool: frames in the ring, in per-CPU caches, in flight |
| `netconsole` | Show netconsole target, buffered bytes, drop/send counters |
| `icmpstat` | Show ICMP statistics |
| `tcpstat` | Show TCP connections and statistics: each connection's state, `snd=` what waits to go and what is in flight, `rcv=` what waits to be read of how big a buffer -- 8 KiB, or a bulk connection's up to 512 KiB -- `wnd=` the window last offered, and `scale=` this end's shift and the peer's when the window is scaled (RFC 7323) |
| `wget [-o <path>] <url> [path]` | Fetch a URL via HTTP or HTTPS GET (follows redirects, including http→https). With a path — `-o` and the trailing argument are the same thing — the body is streamed to that file as it arrives, with no cap but the filesystem's — a VM's disk image of gigabytes is fine, and a disk that fills ends the download as a failed write — with a progress line now and then (how much, of how much when the server said, and how fast: every 2 s at first, every 30 s at most) and the time it took at the end. Without one it is printed, and kept in memory, so it is capped at 32 KiB. HTTPS verifies the certificate chain against the built-in roots and the wall clock; see [HTTPS](tls.md) |
| `udpsend <ip> <port> <msg>` | Send a UDP packet |
| `ping <ip\|hostname>` | Send 5 ICMP echo requests with RTT (resolves hostnames via DNS) |
| `nslookup <hostname>` | Resolve hostname to IP via DNS |
| `dnsflush` | Flush DNS cache |
| `dhcp [dev]` | Obtain IP address via DHCP |
| `random [len]` | Get random bytes as hex string, 1..1024, default 16 — from the kernel's ChaCha20 pool, not from a device |
| `entropy [reseed]` | Show the random pool (seeded, whether hardware entropy reached it, reseeds, bytes generated) and the registered entropy sources; `reseed` draws from every source again first. See [Randomness](random.md) |
| `format nanofs <disk>` | Format disk with nanofs. Refused, like `diskwrite`, on a device in use |
| `mount ramfs <path>` | Mount a ramfs at path |
| `mount nanofs <disk> <path>` | Mount nanofs from disk at path |
| `mount ext2 <disk> <path> [ro]` | Mount ext2 from disk at path, read-write unless `ro` (or unless the image carries features the driver does not write; see [Filesystems](filesystems.md)) |
| `umount <path>` | Unmount filesystem |
| `mounts` | List mount points |
| `ls [path]` | List directory contents (default `/`) |
| `find [path...] [expression]` | The files and directories under each path (`/` when none is given), the path itself included, that the expression holds for -- one a line, a directory before what is in it, as find(1) prints them. Tests: `-name`, `-iname`, `-path`, `-ipath <pattern>` -- the last component, or the whole path as printed, against a shell pattern (`*`, `?`, `[a-z]`, `[!...]`, `\` for the next character as itself; `*` matches `/` in a path; the `i` forms take ASCII letters in either case); `-type f\|d`; `-size [+\|-]N[c\|K\|M\|G\|T]` -- a file of more than, fewer than or exactly N bytes, not find(1)'s blocks of 512, and never a directory; `-empty` -- a file of no bytes or a directory of no entries. Options, anywhere in the expression: `-maxdepth N` and `-mindepth N` (the path given is depth 0), `-xdev` -- not into a directory another filesystem is mounted on. Joined by `!` or `-not`, `-a` or `-and` (or nothing) and `-o` or `-or`, and grouped by `(` and `)` -- each its own word. The shell has no quotes, so a pattern is a word as typed: `find /lib -name *.ko`. There are no actions: what it holds for is printed. A directory the filesystem cannot read is said, never taken for an empty one; `find -help` lists the tests |
| `cp [-r] <src> <dst>` | Copy a file, or a whole directory tree with `-r`; a `dst` that is an existing directory takes the copy under its own name |
| `cat <path>` | Show file contents |
| `write <path> <text>` | Write text to file (creates if needed) |
| `mkdir <path>` | Create directory |
| `touch <path>` | Create empty file |
| `rm <path>` | Remove file or directory (recursively); `del` is the same command |
| `append <path> <text>` | Append text to a file (created if missing) |
| `mv <old> <new>` | Rename or move a file or directory within one filesystem |
| `stat <path>` | Type, size and inode number |
| `truncate <path> <size>` | Cut a file to `size` bytes (a `K`, `M`, `G` or `T` suffix), or grow it there with a hole, made first if it is not there -- a blank disk image for a guest, of any size the filesystem holds; refused past what a file can be there |
| `sync` | Flush every mounted filesystem to disk |
| `fstest [dir] [size]` | Filesystem self-test in `dir` (default `/`) with a big file of `size` bytes (`K`/`M` suffix; default 300 KiB, at least 8 KiB); `fstest / 5M` reaches the doubly-indirect blocks at 4 KiB blocks |
| `crc32 <path>` | CRC-32 of a file, to check a copy against the host |
| `sha256 <path>` | SHA-256 of a file, printed the way `sha256sum` prints it, to check a downloaded kernel against the `SHA256SUMS` of its release |
| `grubenv <path> [name=value ...]` | Show, or set, the variables of a GRUB environment block — the `grubenv` file `grub-editenv` makes and GRUB's `load_env`/`save_env` read and write; `name=` with nothing after it removes one. Edited in place at the same size, the way GRUB's own writer edits it, so GRUB can still read and clear what was set; a block with a line it cannot be sure of reading as GRUB does -- no `=` before the line's end, a name longer than 64 characters or holding a backslash or a NUL -- is listed as far as that line and never written. What arms a one-shot boot of a downloaded kernel from inside nos: see [Real hardware](real-hardware.md#updating-the-kernel-from-inside-nos) |
| `insmod <path> [params]` | Load a kernel module — a Rust crate built into a `.ko` by `make modules` — from a file, and run its init, in a task of its own, the rest of the line its parameters (`insmod /hv.ko vms=/data/vms`): the module's to take, or to refuse saying why -- one that takes none refuses any. Says why when it refuses one: not a module, another machine's, built against another kernel interface, an import the kernel does not export, a name already loaded or still loading or unloading. A load not done in five seconds carries on in the background, the kernel log saying how it ended. See [Loadable modules](modules.md) |
| `rmmod <name>` | Unload a module in a task of its own: run its exit, which releases everything it holds, then free its code. The exit waits for a call of one of the module's commands still running; past five seconds the shell leaves it to finish in the background |
| `blkload <dev> [randread\|randwrite\|read\|write] [bs=4k] [qd=1] [secs=5] [force]` | From the `blkload` module, once it is loaded: a short load test on a disk or a partition — IOPS, bandwidth, latency min/avg/p50/p90/p99/p99.9/max. A write test claims the device first: refused while a mounted filesystem, the disk log or another write test holds it — or the disk it is on, or one of its partitions — and without `force` on a disk with partitions or a device holding a filesystem, a partition table or a disk log area. See [Loadable modules](modules.md#blkload) |
| `netload start [port] [sink]` / `netload send <ip> <port> [size=64] [pps=0] [secs=0] [count=0] [tasks=1] [sport=9998]` | From the `netload` module, once it is loaded: a UDP load test from either end, so `profile` has something to look at other than an idle machine. `start` is the target: it echoes every datagram from the receive softirq (or drops it, in sink mode; port 9999 unless told), and can be driven from a host too, with `scripts/netload.py` (`--pps` to hold a rate, `--threads` to raise the ceiling). `send` is the source: `tasks` senders build datagrams of `size` bytes of payload straight into frames off the pool and hand them to the NIC a batch at a time -- as fast as it takes them, or `pps` a second -- until `count` are sent, `secs` have passed or `netload stop`; what comes back to `sport` is counted as echoes and never answered. It leaves room in the transmit queue for everybody else, so the shell goes on answering under it. See [Loadable modules](modules.md#netload) |
| `netload` / `netload stop` / `netload reset` | What the target and the source have counted -- packets, bytes, failures, rates, and which CPUs did the work; stop both; clear the counters |
| `netblk start <disk> <port> [ro] [nic=eth0] [mtu=1500] [cpu=N] [poll=us]` | From the `netblk` module, once it is loaded: serve an NVMe disk, or a partition of one, over UDP on `port` (1024 and up, one instance to a port), zero-copy. Read-write claims the device the way a `blkload` write test does; `ro` takes no claim. A port someone else has is refused. `poll` keeps the worker spinning that long for the next request before it sleeps. See [netblk](netblk.md) |
| `edit <file>` | From the `edit` module, which the image's `/etc/rc` loads: a text editor, for an SSH session with a terminal (`ssh -t <host> edit <file>`, or the shell `ssh <host>` gives) -- a Mac's keys on Control: `^S` save, `^Q` quit, `^F` find, `^G` go to a line, `^Z`/`^Y` undo and redo, `^X`/`^C`/`^V` the selection or the line, Shift with a move to select, `^A`/`^E`, `⌥←`/`⌥→`. A file comes back out as it went in, byte for byte; a save writes the new content whole before it takes the old one's place, a file changed on disk since it was read is asked about first, and changes left when the connection goes are kept in `<file>.save`. Refused on the console and the UDP shell, which have no terminal to draw on. See [Loadable modules](modules.md#edit) |
| `hv [info]` / `hv on [cpu\|all]` / `hv off [cpu\|all]` / `hv run <guest\|all> [cpu]` | From the `hv` module, once it is loaded: the CPU's virtualization extension, and guests under it. `hv` says which extension the machine has and which CPUs it is on for -- asked of the CPUs themselves, by an IPI that reads the register, so a disagreement with what the module turned on is reported rather than hidden -- and how many times guests switched on a CPU, with whether an IBPB went between each two; under AMD-V whether automatic IBRS is on, and under VT-x what the CPU the command runs on does for its speculation around every entry -- enhanced or legacy IBRS, BHI_DIS_S, VERW, the L1D flush -- with a warning for any CPU whose IA32_SPEC_CTRL no longer has what `hv on` set there, read from each CPU's register. `hv info` adds everything the CPU said about it, a feature a line: nested paging, next-RIP save, ASIDs, x2APIC, 2 MiB nested pages, 1 GiB pages, and on arm64 the exception level the kernel is at and what stage-2 would translate into -- and the huge pool every guest's memory comes from when the boot reserved one (`hugepages=`), its 2 MiB pages free of how many. `hv on` and `hv off` turn it on and off for one CPU or every running one; `rmmod` turns it off for all of them. `hv run` runs a built-in guest (`exits`, `uart`, `hypercall`, `fault`, `absent`, `mmio`, `triple`, `refused`, `spin`, `tpr`, `asid`, `smp`, `ioapic`, `debug`, `cr4`, `msr`, `dr`), or all of them, each in a VM of its own on a task bound to `cpu` when one is named, and says what it did and whether that was what it was told (x86-64, AMD-V). See [The hypervisor](hypervisor.md) |
| `hv boot <kernel> [mem=MiB] [cpus=N] [secs=N] [cpu=N] [xapic] [ioapic] [initrd=path] [disk=path[:ro]]... [input=...] [cmdline=...]` | A Linux guest for `secs` (60 by default): the kernel -- a `bzImage`, or a PVH ELF such as `/lib/hvboot`, which boots the kernel the guest's own disk's `grub.cfg` names (see [A guest's own kernel](hypervisor.md#a-guests-own-kernel-pvh-and-hvboot)) -- and initrd read from files into its memory -- `mem=` MiB of it, 64 to 524288, below the devices' pages and the rest from 4 GiB, and the huge pool's when the boot reserved one (`hugepages=`; see [How much of it, and where](hypervisor.md#how-much-of-it-and-where)) -- run on a vCPU -- or with `cpus=N` on N of them, up to 16, each on a host CPU of its own, the first on `cpu` (see [More than one CPU](hypervisor.md#more-than-one-cpu)); `xapic` has their local APICs come out of reset in xAPIC mode, reached through the page, for a kernel that reads it before it looks at the mode firmware left (see [MMIO](hypervisor.md#mmio)); `ioapic` gives a guest of more than one CPU an IO-APIC, its devices' interrupts routed through it to any CPU and its local APICs in xAPIC mode (see [The IO-APIC](hypervisor.md#the-io-apic)) -- then its console and how it ended printed, the console also going to the kernel log a line at a time (`hvguest| ...`) as it runs: a thousand lines at once and fifty a second after, what is left out said once a second at most. `input=` is typed at its shell once it has one, `\n` for a newline (x86-64, AMD-V). See [A Linux guest](hypervisor.md#a-linux-guest) |
| `hv start <kernel> [mem=MiB] [cpus=N] [cpu=N] [xapic] [ioapic] [initrd=path] [disk=path[:ro]]... | `hv cores [own\|shared]` | Whether a guest's cores are its own -- whole cores no other guest has a CPU on, its vCPUs or the task serving its disks, its vCPUs filling their threads, and a guest that would need another's core refused -- or may be shared, as before (`own`, the default, at every load); and which guest holds which CPUs. Guests running keep where they are (x86-64). See [The hypervisor](hypervisor.md#more-than-one-cpu) |
| `hv forward [add <port> <vm> <guest-port> \| del <port>]` | A port of nos's relayed to a port of a `net` guest's -- how a guest's server is reached from outside. `hv forward` alone lists them, with the connections each has carried (x86-64, AMD-V). The other way, a `net` guest reaches what nos reaches through NAT, and the switch answers its DHCP: `hv list` says which address the guests go out from and counts the DHCP answers. IPv6 goes between the guests only, in the prefix the switch's router advertisement gives them: `hv list` counts the advertisements and the addresses bound to the guests' ports. See [A network](hypervisor.md#a-network) |
| `hv help` | Every `hv` subcommand, a line each |
| `netblk list` / `netblk stop <port>\|all` | The instances served and their counters; stop one, or all -- waiting for what the disk still has in flight |
| `lsmod` | List the modules: name, size, load address, how many kernel functions each binds to, and which are permanent, still loading or still unloading. Never waits on a load or unload in progress |
| `rc [add <line>\|del <n>\|clear\|run]` | Show or edit `/etc/rc`: shell commands, a line each (blank lines and `#` comments skipped), that the shell's task runs once at boot after DHCP -- how a module such as [sshd](sshd.md) gets loaded and started on a machine nobody can reach until it is. `rc` numbers the lines, `add` appends one, `del` takes one out, `clear` removes the file, `run` runs it now. What it prints at boot goes to the kernel log and the screen; `rc=off` skips it |
| `usb` | Show xHCI controllers, connected root ports and keyboard report counters |
| `panic [type]` | Trigger kernel panic: direct, or `pf` (page fault), `div0` (divide by zero), `ud` (invalid opcode), `df` (a real double fault, x86-64: a stack pointer no access can use, the report from the IST stack), `offstack` (a panic on a stack that is no task's, with preemption on) -- the last two what `panic-test.sh` drives |
| `version` | Show kernel version |
| `poweroff` / `shutdown` | Power off (ACPI S5) |
| `reboot` | Reset system (keyboard controller) |

## Line editing

At the console -- the screen with its PS/2 or USB keyboard, or a terminal on
the serial port -- and in an [SSH](sshd.md) session with a terminal, a line
is edited with the same keys:

| Key | What it does |
|-----|--------------|
| Enter | Runs the line |
| Backspace | Takes back the last character |
| Up, Down (^P, ^N) | Back through the last 32 lines run, and forward again to the one being typed |
| ^R | Searches back through them for a line that holds what is typed after it, as bash's `(reverse-i-search)'query': line`. ^R again finds the next older one, Backspace takes a character off the query, Enter runs what was found, ^G puts back the line from before the search, and any other key -- an arrow, ^U -- keeps what was found, to be edited |
| ^C | Drops the line |
| ^U | Clears it |

A line of nothing but spaces is not kept, nor the same line twice running.
The console's history is its own and each SSH session's is its own; none
outlives the boot. Over SSH, ^L also clears the screen and ^D on an empty
line logs out. A console line is at most 80 characters, an SSH one 255.

The keyboards send what a terminal would -- an arrow as ESC [ A..D, Ctrl and
a letter as its control byte -- so the console's editor
(`src/base/kernel/line_editor.cpp`) reads a keyboard as it reads the serial
port; the screen knows only text and Backspace, and a line is redrawn by
erasing back to where it changed. `scripts/udpsh.py`, the UDP shell's
client, edits on the host with readline -- the same keys -- and keeps its
history in `~/.nos_udpsh_history`.
