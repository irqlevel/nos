Это руководство покажет, как остановить работающий nos в GDB и посмотреть, где находится каждый CPU. Ещё вы научитесь читать отчёт о панике, включать подробный лог для одной подсистемы, сужать круг причин неудачной загрузки параметрами ядра и доставать лог с машины, у которой нет последовательного порта.

Что понадобится:

- [собранное](/howto/build) ядро; скрипты GDB загружают `bin/kernel64.elf` или `bin/kernel-arm64.elf`;
- QEMU (см. руководство [«Запуск nos в QEMU»](/howto/run-in-qemu));
- GDB для x86-64. Для arm64 — GDB с поддержкой aarch64 (`gdb-multiarch` или `aarch64-elf-gdb`) либо LLDB.

## Подключение GDB к QEMU

### x86-64

`qemu.sh`, `qemu-disk.sh` и `run.sh` запускают QEMU с ключом `-s`. С ним QEMU открывает на TCP-порту 1234 свой встроенный GDB-сервер. Пока один из этих скриптов работает, запустите GDB:

```sh
./scripts/gdb64.sh
```

Скрипт запускает GDB с командами из [`scripts/gdb-debug64`](https://github.com/irqlevel/nos/blob/master/scripts/gdb-debug64):

```text
set architecture i386:x86-64
target remote 127.0.0.1:1234
symbol-file bin/kernel64.elf
set print pretty on
set height 20000
thread apply all bt
```

QEMU показывает GDB каждый виртуальный CPU как отдельный поток, поэтому последняя команда печатает бэктрейс каждого CPU. Если машина перестала отвечать, начинать стоит именно с этого. Затем GDB оставляет вас в своём приглашении, а машина стоит. `info threads`, `thread N`, `bt`, `break` и `continue` работают как обычно, а Ctrl-C снова останавливает машину. То же самое без скрипта:

```sh
gdb -ex "symbol-file bin/kernel64.elf" \
    -ex "set architecture i386:x86-64" \
    -ex "target remote :1234"
```

C++ компилируется с полной отладочной информацией (`-g3`). Код на Rust собирается в staticlib в релизном режиме и без неё, поэтому во фрейме Rust GDB покажет имя функции, но не строку исходника.

Чтобы отлаживать с самой первой инструкции, добавьте к `-s` ключ QEMU `-S`. Тогда QEMU ничего не выполняет, пока не подключится GDB. `qemu.sh` не принимает дополнительных аргументов, поэтому запустите его команду QEMU вручную:

```sh
qemu-system-x86_64 -smp 2 -cdrom nos.iso -serial file:nos.log -s -S
```

### arm64

`qemu-arm64.sh` передаёт свои аргументы QEMU:

```sh
./scripts/qemu-arm64.sh -s -S
```

Затем в другом терминале:

```sh
./scripts/gdb-arm64.sh
```

Скрипт запускает `gdb-multiarch` (или `aarch64-elf-gdb`, если у вас установлен он) с командами из [`scripts/gdb-debug-arm64`](https://github.com/irqlevel/nos/blob/master/scripts/gdb-debug-arm64). Этот файл делает то же, что и вариант для x86-64, но загружает `bin/kernel-arm64.elf`. Чтобы запустить ядро, введите `continue`. Если ни один из этих GDB не установлен, скрипт сообщит об этом и предложит LLDB:

```sh
lldb bin/kernel-arm64.elf
```

В приглашении LLDB подключитесь командой `gdb-remote 1234`.

## Как читать отчёт о панике

Отчёт о панике уходит в последовательный порт и на экран. Если включены netconsole и дисковый лог, он попадает и туда. CPU, на котором случилась паника, останавливает остальные CPU. После этого машина стоит с отчётом на консоли, если только её не загрузили с `panic=N`. В этом случае она перезагружается через N секунд (1–3600) после того, как отчёт ушёл. Вот формат отчёта, строка за строкой, как его печатает [`kernel/panic.cpp`](https://github.com/irqlevel/nos/blob/master/src/base/kernel/panic.cpp):

```text
PANIC:<function>():<file>,<line>: <message>
CPU: <index>
Task: pid <pid> name <task>
Backtrace:
  [0] 0x<address> <function>+0x<offset>
  [1] 0x<address> <function>+0x<offset>
Modules: <name> 0x<base>+0x<size>
Cpu <index> backtrace:
  [0] 0x<address> <function>+0x<offset>
```

- Первая строка говорит, где случилась паника и почему. Для нарушенного инварианта, пойманного `BUG_ON`, там будет `BUG`. Для исключения процессора там будет то, что сообщил CPU: `EXC: PageFault cr2 0x... rip 0x... rsp 0x... err 0x... cr3 0x...` на x86-64 или `sync exception: ... (esr 0x... ec 0x... iss 0x...) far 0x... elr 0x...` на arm64. Паника в Rust начинается с `RUST PANIC: panicked at <file>:<line>:<column>:`, а за этим идёт её сообщение.
- `Backtrace` — стек CPU, на котором случилась паника. Имена функций ядро определяет само, по встроенной в образ таблице символов, так что файл символов не нужен. Каждый фрейм — это адрес возврата, и назван он по вызову, который стоит прямо перед ним.
- Фрейм в коде модуля заканчивается именем модуля в квадратных скобках. Если загружен хотя бы один модуль, в отчёте есть ещё строка `Modules:` с диапазоном адресов каждого модуля. По ней можно определить фрейм, который больше ничем не назван.
- На x86-64 ядро запрашивает стеки остальных CPU, посылая им NMI. Каждый ответ идёт следом в виде `Cpu N backtrace:`. CPU, который не ответил, тоже называется по номеру (`Cpu N did not answer the NMI`).
- Фрейм, напечатанный голым адресом, лежит вне кода ядра и вне всех загруженных модулей.

Пример из раздела [Backtraces](/docs/modules#backtraces):

```text
Backtrace:
  [0] 0xFFFF800012DA1C40 mod_hello::init::{closure#0}+0x3c [hello]
  [1] 0xFFFF80000104A2F1 kernel::Cmd::dispatch_dynamic+0xd1
...
Modules: hello 0xFFFF800012DA0000+0x5000
```

Некоторые зависания превращаются в панику, чтобы о них появился отчёт. Если спинлок держат слишком долго, ядро паникует с сообщением `Spinlock 0x... stuck, held ... ns`. Если на TLB shootdown нет ответа десять секунд, ядро паникует и называет CPU, которые не ответили.

Чтобы посмотреть на отчёт о панике на одноразовой виртуальной машине, в шелле есть команды `panic` (прямая паника), `panic pf` (page fault) и `panic ud` (недопустимая инструкция).

Если задача жива, но застряла, `ps` покажет список задач, а `bt <pid>` напечатает бэктрейс одной из них. Для этого `bt` посылает IPI тому CPU, на котором задача выполняется. `stacks` показывает самую глубокую точку, до которой доходил каждый стек.

## Лог ядра и уровни трассировки

Каждая строка трассировки выглядит так: `level:seconds.microseconds:function(),file,line: message`. Она попадает в лог ядра и в последовательный порт, а если включены netconsole и дисковый лог, то и туда. Когда шелл запущен, строки трассировки в консоль больше не выводятся. Читайте их через `dmesg [lines] [filter]`, например `dmesg 40` или `dmesg 100 virtio`.

Строка печатается, если её уровень не выше текущего уровня трассировки. Уровень бывает от 0 до 5, по умолчанию он равен 1. Изменить его можно двумя способами:

- `loglevel=N` в командной строке ядра. Только так можно получить подробности о самой загрузке.
- `loglevel N` в шелле работающего ядра. `loglevel` без аргумента показывает текущий уровень. Команда работает и через UDP-шелл, и по SSH, а это важно на машине, где другой консоли нет.

У самых многословных подсистем свои уровни. Они заданы константами в начале [`src/base/kernel/trace.h`](https://github.com/irqlevel/nos/blob/master/src/base/kernel/trace.h):

| Уровень | Константы | Что видно на этом уровне |
|---|---|---|
| 0 | `EXC_LL`, `ACPI_LL`, `CMD_LL`, `LAPIC_LL`, `IO_APIC_LL` | печатается всегда |
| 3 | `KBD_LL`, `USB_LL`, `TEST_LL`, `ICMP_LL`, `TASK_LL`, `MODULE_LL` | клавиатура и USB, тест многозадачности, три строки на каждый ping, создание и удаление каждой задачи, к чему привязан каждый импорт модуля |
| 4 | `PAGE_ALLOCATOR_LL`, `ALLOCATOR_LL`, `POOL_LL`, `MM_IO_LL` | аллокаторы (каждое выделение памяти) и MMIO; очень многословно |

Чтобы видеть одну подсистему без остальных, понизьте её константу и пересоберите ядро. Код на Rust пишет в лог через `trace!(level, ...)`, по той же шкале.

## Поиск причины неудачной загрузки

Где задаётся командная строка ядра, зависит от способа загрузки:

| Загрузка | Где | Что затем |
|---|---|---|
| x86-64 с ISO | строка `multiboot2` в `build/grub.cfg` | пересобрать `nos.iso` |
| x86-64 с образа диска | строка `multiboot2` в `build/grub-disk.cfg` | заново запустить `./scripts/build-disk.sh` |
| arm64 в QEMU | `APPEND=` в `scripts/qemu-arm64.sh` | загрузиться снова |
| сервер, развёрнутый из системного образа | ключ `--cmdline "ARGS"` у `nos-install` | см. [«Установка nos на выделенный сервер»](/howto/install-on-a-server) |

Командная строка не может сорвать загрузку: неизвестный ключ или значение ядро запишет в лог и пропустит. Длина строки ограничена 255 символами. Исключайте из загрузки лишнее, по одному шагу за раз:

1. `smp=off`: только загрузочный CPU. Если так ядро загружается, проблема в запуске остальных CPU.
2. `maxcpus=2`: загрузочный CPU и ещё один, потом больше. SMP остаётся, но число запускаемых CPU ограничено.
3. `loglevel=4`: всё, что делает загрузка, включая выделения памяти.
4. Затем подсистемы, по одной:
   - `usb=off` (x86-64): не инициализировать xHCI;
   - `its=off` (arm64): отключить GICv3 ITS; PCIe обходится без MSI, а virtio-mmio он не нужен;
   - `hwrng=off`: не использовать инструкцию процессора для случайных чисел;
   - `rc=off`: не выполнять `/etc/rc`, чтобы обойти строку в нём, из-за которой машина не поднимается;
   - `dhcp=off`: полностью отключить DHCP;
   - `console=serial` или `console=vga`: оставить шелл только на одной консоли.

На x86-64 загрузка, которая падает раньше, чем появилась хоть какая-то консоль, печатает на экране `ERR:` и цифру. Это значит, что не прошла одна из ранних проверок в `boot64.asm`: Multiboot, CPUID или long mode.

Все параметры перечислены на странице [«Параметры ядра»](/docs/kernel-parameters), а что происходит между маркерами, объясняет страница [«Загрузка»](/docs/boot).

## Лог с машины без последовательного порта

На ноутбуке, облачной виртуальной машине или выделенном сервере часто нет последовательного порта, который можно читать. Вот что nos предлагает взамен:

- **Netconsole** — для загрузки, которая доходит до сети. Загрузите ядро с `netconsole=ip:port dhcp=auto nctail=64` и запустите на принимающей машине `python3 scripts/netconsole.py -o boot.log`. С `nctail=64` машина, у которой после появления связи осталось мало времени, тратит его на самые свежие строки. Лог приходит с первой строки загрузки, и в него попадает отчёт о панике, если MAC-адрес сборщика уже известен. Как всё настроить, рассказано в руководстве [«Подключение к работающему nos»](/howto/connect).
- **Дисковый лог** — для загрузки, которая останавливается раньше, чем поднимется сеть. Под Linux на этой машине подготовьте область для лога на свободном разделе. Затем загрузите nos с `disklog=on`, а при следующей загрузке Linux прочитайте лог:

  ```sh
  sudo ./scripts/disklog.py format /dev/nvme0n1p1
  sudo ./scripts/disklog.py read /dev/nvme0n1p1
  ```

  `format` откажется работать с устройством, на котором, судя по всему, ещё есть файловая система, часть RAID-массива или swap. Без `disklog=on` nos даже не читает диски в поисках этой области. С ним, но без подготовленной области, загрузка пишет в лог `DiskLog: disklog=on, but no prepared area on any disk` и идёт дальше. Команда шелла `disklog` показывает, что нашлось.
- **Экран.** `trace=vga` (x86-64) выводит лог загрузки не только в последовательный порт, но и на экран. На машине без UART так происходит и по умолчанию.
- **`panic=N`.** Машина, у которой единственная консоль — сеть, возвращается через N секунд после паники, а не остаётся стоять там, где её никто не видит.

Как эти средства применялись на трёх машинах, где работает nos, рассказано на странице [«Реальное железо»](/docs/real-hardware).

## Сборка с проверками неопределённого поведения

Если загрузка зависает в каком-то постороннем месте и только на одной архитектуре, причиной может быть неопределённое поведение, которое проявилось далеко от того места, где возникло. Соберите ядро с включёнными проверками и загрузите так же:

```sh
make nocheck UBSAN=1 RUSTUB=1
./scripts/smoke-test.sh --skip-build
```

Первая же операция с неопределённым поведением в C++ вызывает панику с указанием места. В Rust базовая библиотека `core` проверяет предусловия unsafe-операций, и первое нарушенное предусловие вызывает такую же панику. С `ubsan=warn` в командной строке ядро вместо этого печатает все отчёты C++ за загрузку и продолжает работу. Каждое место попадает в отчёт один раз, с бэктрейсом. Подробнее об этом в руководстве [«Сборка nos»](/howto/build).

## Самотесты при загрузке

Самотесты выполняются при каждой загрузке из `Test()` в [`src/base/kernel/test.cpp`](https://github.com/irqlevel/nos/blob/master/src/base/kernel/test.cpp). Упавший тест вызывает панику `Self test failed`. Чтобы запустить только один тест, измените `Test()` так, чтобы она вызывала только его функцию, затем пересоберите ядро, загрузите его и следите за `nos.log`.

## Решение проблем

- **`target remote` не подключается.** QEMU запущен без `-s`, или порт 1234 уже занят другим QEMU. Пользоваться портом одновременно может только один QEMU.
- **`gdb-arm64.sh` выводит `No aarch64 GDB found`.** Установите `gdb-multiarch` или `aarch64-elf-gdb` либо используйте LLDB, как показано выше.
- **Нет файла `bin/kernel-arm64.elf`.** Сборка ISO для x86-64 удаляет и заново создаёт `bin/`. Тот же ELF лежит в корне репозитория, так что скопируйте его обратно: `cp kernel-arm64.elf bin/`.
- **Символы в GDB не совпадают с тем, что выполняется.** Загружайте ELF из той же сборки, что и запущенный образ. После пересборки перезапустите и QEMU, и GDB.
- **`loglevel 4` заваливает всё сообщениями.** На этом уровне трассируется каждое выделение памяти, и каждая строка к тому же уходит в последовательный порт. Вернуть уровень по умолчанию можно командой `loglevel 1`.
- **Отчёт о панике так и не дошёл до netconsole.** Во время паники отчёт уходит, только если MAC-адрес сборщика есть в кэше ARP. Загружайтесь ещё и с `disklog=on` и подготовленной областью или используйте `panic=N`, чтобы машина вернулась.
