К концу этого руководства у вас будет свой модуль. Это крейт в `src/crates/modules/`, который собирается в файл `.ko` и регистрирует команду шелла. Вы загрузите его в работающий nos командой `insmod` и выгрузите командой `rmmod`, не пересобирая и не перезагружая ядро.

Что понадобится:

- дерево nos и рабочая сборка, нативная или в Docker ([Сборка nos](/howto/build));
- nos, в который вы будете загружать модуль, например в QEMU ([Запуск nos в QEMU](/howto/run-in-qemu));
- немного Rust: модули — это крейты `#![no_std]`.

## Что такое модуль

- **Модуль пишется только на Rust.** Это крейт типа `staticlib`, который сборка линкует в позиционно-независимый разделяемый объект ELF, то есть в файл `.ko`.
- **С ядром модуль общается через один API.** Это функции `extern "C"`, объявленные в крейте `ffi`, и безопасные обёртки над ними из `kcore`. Тем же API пользуются драйверы, встроенные в ядро. Загрузчик связывает модуль с таблицей экспорта, сгенерированной из этих объявлений, и отвергает всё остальное.
- **`insmod` вызывает init модуля, а `rmmod` уничтожает состояние, которое вернул init.** Выходом модуля служит его `Drop`, так что отдельную функцию выгрузки писать не нужно.
- **В модули выносят необязательное.** Всё, без чего машина может обойтись (сервер, генератор нагрузки, диагностику), делают модулем. `sshd`, `netblk`, `netload`, `blkload`, `heapbench` и гипервизор `hv` — всё это модули.
- **Модуль не может быть драйвером диска или сетевой карты.** Такие драйверы регистрируются в своём слое как trait-объекты Rust изнутри образа ядра, и нет C-имени, к которому модуль мог бы привязаться. Модуль пользуется дисками и сетевыми картами, но сам их не предоставляет.

## Самый маленький настоящий модуль: `hello`

В `src/crates/modules/hello/` два файла. Первый — `Cargo.toml`:

```toml
[package]
name = "mod-hello"
version = "0.1.0"
edition = "2021"

[lib]
name = "mod_hello"
crate-type = ["staticlib"]

[dependencies]
kmod = { path = "../../kmod" }
kcore = { path = "../../kcore" }
```

Второй — [`src/lib.rs`](https://github.com/irqlevel/nos/blob/master/src/crates/modules/hello/src/lib.rs), здесь он показан без doc-комментария:

```rust
#![no_std]

extern crate alloc;

use alloc::boxed::Box;
use core::fmt::Write;
use core::sync::atomic::{AtomicU64, Ordering};
use kcore::cmd::Command;

static CALLS: AtomicU64 = AtomicU64::new(0);

struct Hello {
    _cmd: Command,
}

impl kmod::Module for Hello {}

impl Drop for Hello {
    fn drop(&mut self) {
        kcore::trace!(0, "hello: unloaded after {} calls", CALLS.load(Ordering::Relaxed));
    }
}

fn init() -> kcore::error::Result<Box<dyn kmod::Module>> {
    let cmd = Command::register("hello", "hello [name] - a command from a loadable module", |args, out| {
        let calls = CALLS.fetch_add(1, Ordering::Relaxed) + 1;
        let who = if args.is_empty() { "world" } else { args };
        let _ = writeln!(out, "hello, {} -- call {} since the module was loaded", who, calls);
    })?;

    kcore::trace!(0, "hello: loaded");
    Ok(Box::new(Hello { _cmd: cmd }))
}

kmod::module!(name: "hello", init: init);
```

Разберём по частям:

- **`kmod::module!(name: "hello", init: init)`** задаёт имя модуля и говорит `insmod`, какую функцию вызвать. Это имя показывает `lsmod` и принимает `rmmod`. В нём может быть не больше 31 печатного символа, а с более длинным именем сборка не пройдёт. Ещё макрос создаёт `nos_module_info` — заголовок, который ищет загрузчик.
- **`init`** создаёт состояние модуля и возвращает его как `Box<dyn kmod::Module>`. Если `init` вместо этого вернёт ошибку, `insmod` завершится неудачей, а в логе ядра появится `module init failed: ...`.
- **`Hello` — это состояние модуля.** Оно владеет всем, что модуль зарегистрировал. Пока `Hello` держит `Command`, команда остаётся зарегистрированной. `rmmod` уничтожает `Hello`, а вместе с ним и `Command`, который при этом снимает команду с регистрации. Любая отмена регистрации в `kcore` сначала дожидается обратного вызова, который ещё выполняется на другом CPU. Поэтому код команды никогда не освобождается, пока она работает. `Drop` здесь только добавляет строку в лог.
- **`impl kmod::Module for Hello {}`** требует `Send`, потому что состояние переходит из рук в руки: строит его задача, выполняющая `insmod`, а уничтожает задача, выполняющая `rmmod`.
- **`Command::register(name, help, handler)`** добавляет команду в шелл, где бы он ни работал: в консоли, в UDP-шелле или в сеансе SSH. Обработчик имеет тип `Fn(&str, &mut Output) + Send + Sync + 'static`. Он получает остаток командной строки и `Output`, реализующий `core::fmt::Write`. От текста справки ядро хранит не больше 95 символов. Если имя уже занято, `register` вернёт ошибку, а `?` превратит её в неудачный `insmod`.
- **`static CALLS`** принадлежит только этому модулю. У каждого модуля своя копия `kcore`, поэтому общих статических переменных у модулей нет и вызывать друг друга они не могут.

Остальное `kmod` реализует один раз для всех модулей. Глобальный аллокатор модуля — это куча ядра. Обработчик паники из `kmod` превращает панику в модуле в панику ядра. И `kmod` же даёт заголовок с магическим числом, версией формата, именем, init, exit и хешем интерфейса ядра.

## Свой модуль

Скопируйте `hello` и дайте копии своё имя. Пусть это будет `greet`:

```sh
cp -r src/crates/modules/hello src/crates/modules/greet
```

В `src/crates/modules/greet/Cargo.toml` переименуйте пакет в `mod-<name>`, а библиотеку в `mod_<name>`. Makefile рассчитывает именно на такие имена: он собирает пакет `mod-greet` и линкует `libmod_greet.a`.

```diff
 [package]
-name = "mod-hello"
+name = "mod-greet"
 version = "0.1.0"
 edition = "2021"

 [lib]
-name = "mod_hello"
+name = "mod_greet"
 crate-type = ["staticlib"]
```

Добавьте крейт в `members` рабочего пространства в `src/crates/Cargo.toml` (здесь строка сокращена). `default-members` не трогайте: по этому списку собирается само ядро.

```diff
-members = [..., "modules/hv", "modules/heapbench"]
+members = [..., "modules/hv", "modules/heapbench", "modules/greet"]
```

Добавьте имя в `MODULES` в `Makefile`:

```diff
-MODULES = hello modtest slowexit blkload netblk netload sshd hv heapbench
+MODULES = hello modtest slowexit blkload netblk netload sshd hv heapbench greet
```

Наконец, в `src/crates/modules/greet/src/lib.rs` поменяйте имя и текст справки команды, а имя модуля задайте в `kmod::module!(name: "greet", init: init)`.

### Ядро доступно через `kcore`

Модулю доступно всё, что оборачивает `kcore`. Полная карта — в разделе [What `kcore` has](/docs/rust#what-kcore-has). Чаще всего нужно вот это:

| `kcore::` | Что даёт модулю |
|---|---|
| `cmd` | `Command::register`, а также `Output::read_input` для команды, которая читает то, что печатает пользователь SSH |
| `trace` | `trace!(level, ...)` пишет в лог ядра; уровень 0 виден всегда |
| `sync` | блокировки, которые владеют защищаемыми данными (`Mutex<T>`, `SpinLock<T>`, `IrqSpinLock<T>` и другие), а также `Event` и `WaitGroup` |
| `task` | задачи: `spawn_with` и `spawn_on_with` запускают задачу, которая держит `Arc` на состояние модуля; `TaskHandle` при drop дожидается своей задачи; `sleep_ms` |
| `time`, `random`, `cpu` | часы, пул случайных чисел ядра, номера CPU и межпроцессорные прерывания (IPI) |
| `fs` | файлы: `read`, `write`, `create` и `File`, чтобы держать файл открытым |
| `net`, `tcp`, `block` | существующая сетевая карта (UDP-слушатели, кадры), TCP-слушатели и потоки, существующий диск или раздел |
| `timer`, `softirq` | периодический таймер; обработчик soft IRQ. Снять такой обработчик с регистрации нельзя, поэтому он делает модуль **постоянным**, и `rmmod` откажется его выгружать |

Если команде нужно состояние модуля, держите его в `Arc` и перемещайте в обработчик клон. Так модуль гипервизора регистрирует команду `hv`:

```rust
let for_cmd = state.clone();
let cmd = Command::register("hv", HELP, move |args, out| command(&for_cmd, args, out))?;
```

На модули распространяются соглашения проекта. Вот главные правила:

- **Пишите без `unsafe`.** Сначала ищите подходящий тип в `kcore`. Если такого нет, добавьте его в `kcore` один раз и объясните в комментарии, почему он корректен. Места с `unsafe` считает `scripts/unsafe-count.py modules/greet`.
- **Не выделяйте и не освобождайте память, держа спин-блокировку.** Аллокатор страниц сбрасывает TLB на всех остальных CPU и ждёт ответа от каждого. CPU, который крутится на вашей блокировке, работает с выключенными прерываниями и ответить не может. Они ждут друг друга, пока через десять секунд ядро не запаникует и не назовёт CPU, которые так и не ответили. Поэтому соберите под блокировкой то, что нужно освободить, отпустите её и только потом освобождайте.
- **Осторожнее с объектами, которые ждут при уничтожении.** UDP-слушатель, `TaskHandle` или обработчик прерывания при drop дожидаются своих обратных вызовов. Держите каждый такой объект в собственном `Lock<Option<..>>`: забирайте его через `take()` под блокировкой, а уничтожайте уже после того, как её отпустили. Если уничтожить его под блокировкой, которая нужна его ожиданию, получится взаимоблокировка.
- **Никогда не вызывайте `rmmod` из собственной команды модуля.** Выгрузка ждала бы эту команду, а команда ждала бы выгрузку.
- **Модуль может вызывать только то, что объявлено в `ffi`.** Новый сервис ядра добавляется в три шага: функция на C++ в `src/base/kernel/rust_ffi.cpp`, её объявление в `src/crates/ffi` и безопасная обёртка в `src/crates/kcore` ([Adding a kernel service](/docs/rust#adding-a-kernel-service)). От этого меняется хеш интерфейса, поэтому ядро и все модули пересобираются вместе.

## Сборка

```sh
make modules
make modules ARCH=aarch64
```

Эти команды дают `out/x86_64/modules/greet.ko` и `out/aarch64/modules/greet.ko`. Обычные `make` и `make nocheck` тоже собирают модули. На Mac собирайте в контейнере `nos-builder`:

```sh
docker run --platform linux/amd64 --rm -v "$PWD:/src" -w /src nos-builder make modules
```

Каждый модуль компилируется отдельно, в `src/crates/target/modules`, со своей копией `core`, `alloc`, `kcore` и `kmod`. Модулю нужны флаги компилятора, которых нет у Rust-части ядра:

- **позиционно-независимый код**, потому что заранее неизвестно, куда модуль загрузят;
- **малая модель кода на x86**, тогда как само ядро использует большую;
- **собственные `memcpy` и подобные функции из compiler-builtins**, чтобы модуль не импортировал ничего, кроме API ядра.

Затем `ld.lld` линкует модуль как разделяемый объект с `-Bsymbolic`. Каждый сегмент получает собственные страницы, а скрипт версий экспортирует `nos_module_info` и больше ничего. Для трассировок стека сборка добавляет секцию `.nos_syms` с деманглированными именами функций модуля. В итоге `hello.ko` занимает около 25 КиБ.

> Собирайте модуль из того же дерева, что и ядро, в которое будете его загружать. Сборка хеширует исходники крейта `ffi` и записывает этот хеш и в ядро, и в каждый модуль. Загрузчик отвергает модуль, чей хеш не совпадает с хешем ядра. Модуль, собранный в обход Makefile, несёт вместо хеша `unset` и тоже отвергается.

## Как доставить модуль на машину

- **На корневую файловую систему.** Положите `.ko` в каталог и сделайте из этого каталога корневой образ командой `scripts/mkrootfs.sh root.img 64 <dir>`. Подключите образ к QEMU как диск virtio. ISO загружается с `root=auto`, и ядро монтирует как `/` файловую систему с меткой `nos`. Полная команда QEMU есть в [руководстве по Linux-гостю](/howto/linux-guest).
- **По HTTP со своей машины.** Раздайте каталог сборки и скачайте файл из шелла nos. В user-сети QEMU ваша машина доступна по адресу 10.0.2.2:

  ```sh
  python3 -m http.server 8000 --directory out/x86_64/modules
  ```

  ```sh
  wget http://10.0.2.2:8000/greet.ko /greet.ko
  ```

  Без корневого диска `/` — это ramfs, файловая система в памяти, и после перезагрузки файла не будет.
- **Из релиза, если это модуль из дерева.** В каждом релизе есть все модули в виде `<name>-x86_64.ko` и `<name>-arm64.ko`. Берите модуль из того же релиза, что и работающее ядро (какой это релиз, покажет команда `version`):

  ```sh
  wget https://github.com/irqlevel/nos/releases/download/<tag>/hello-x86_64.ko /hello.ko
  ```

На сервере, установленном из системного образа, каталог `/lib/modules` принадлежит образу, и каждое обновление его заменяет. Поэтому свои модули держите в другом месте ([Установка nos на выделенный сервер](/howto/install-on-a-server)).

## Загрузка, работа, выгрузка

Вот сеанс с `hello`, как его записала документация проекта. Ваш модуль поведёт себя так же:

```text
$ insmod /hello.ko
module: hello loaded at 0xFFFF8000...
$ hello nos
hello, nos -- call 1 since the module was loaded
$ lsmod
hello  24 KiB at 0xFFFF8000..., 7 kernel imports
$ rmmod hello
module: hello unloaded
```

- **Лог модуля** попадает в лог ядра, а не в шелл. Посмотреть его можно командой `dmesg 5 hello`.
- **Ожидание в пять секунд.** `insmod` и `rmmod` передают работу отдельной задаче и ждут её не дольше пяти секунд. Если выгрузка длится дольше (например, потому что ещё работает одна из команд модуля), она продолжается в фоне. Пока она идёт, `lsmod` показывает модуль как выгружающийся, а чем она закончилась, сообщит лог ядра.
- **Загрузка при старте.** Команда `rc add insmod /greet.ko` добавит нужную строку в `/etc/rc`. Задача шелла выполняет `/etc/rc`, когда сеть уже поднята.
- **Выключение.** Прежде чем размонтировать файловые системы, `poweroff` и `reboot` выгружают все модули, которые можно выгрузить, начиная с самого нового.

## Что проверяет загрузчик

`insmod` передаёт файл загрузчику из `src/base/kernel/module.cpp`. Загрузчик по порядку проходит следующие шаги и отвергает модуль при первой же неудаче:

1. **Файл.** Это должен быть разделяемый объект ELF64 для этого CPU, little-endian, с заголовками внутри файла и без сегментов thread-local и интерпретатора. Каждый загружаемый сегмент должен быть выровнен по странице, лежать внутри файла, не пересекаться с другими и **никогда не быть одновременно доступным на запись и на исполнение**.
2. **Импорты, ещё до отображения в память.** Загрузчик ищет каждый неопределённый символ в таблице экспорта ядра. Если ядро не может дать модулю всё нужное, загрузчик отвергает модуль и перечисляет, чего не хватает.
3. **Образ.** Загрузчик отображает его на собственные страницы. Вместе с именами функций образ может занимать не больше 16 МиБ.
4. **Релокации.** Загрузчик применяет только три вида: «ничего», «база загрузки плюс addend» и «символ плюс addend». Любой другой вид он отвергает.
5. **Заголовок.** Теперь, когда указатели в нём настоящие, загрузчик проверяет магическое число, версию формата, имя, init и exit, указывающие в собственный код модуля, и хеш интерфейса ядра.
6. **Права страниц.** Каждый сегмент получает права, которые запрашивает его программный заголовок: только чтение, чтение и исполнение или чтение и запись. TLB сбрасывается на всех CPU, а на arm64 ещё и синхронизируются кэши инструкций. Ядро с загруженным модулем остаётся W^X: ни одна страница не доступна одновременно на запись и на исполнение.
7. **Init.** Второй модуль с тем же именем отвергается ещё до этого шага. Неудачный init ничего после себя не оставляет.

Вот какие отказы можно увидеть и что с ними делать:

| Сообщение | Что делать |
|---|---|
| `module: built against another kernel interface (ffi ..., this kernel ...) -- rebuild it from this tree` | Соберите модуль из дерева ядра или возьмите его из релиза ядра. |
| `module: needs <symbol>, which this kernel does not export` | Модуль вызывает то, чего нет в `ffi` этого ядра. Пересоберите ядро и модуль вместе. |
| `module: segment N is both writable and executable` | Соберите `.ko` через `make modules`: при такой линковке каждый сегмент получает собственные страницы и права. |
| `module: no nos_module_info -- not a module built with kmod::module!` | В крейте нет вызова `kmod::module!`. |
| `module: greet is already loaded` | Сначала выполните `rmmod greet`. |
| `module: greet: init failed` | `init` вернул ошибку. `dmesg` покажет строку `module init failed: ...` с причиной. |
| `module: greet is permanent: it imports ..., which nothing undoes` | Модуль зарегистрировал обработчик soft IRQ, поэтому останется в ядре до следующей загрузки. |

В трассировках стека кадры из кода модуля подписаны так же, как кадры ядра, только после них стоит имя модуля, например `mod_hello::init::{closure#0}+0x3c [hello]`. Отчёт о панике заканчивается строкой `Modules:`, где указано, по какому адресу загружен каждый модуль.

## Проверка

- **Каждая загрузка проверяет загрузчик.** На обеих архитектурах самотест при старте ядра подгружает `modtest` — модуль, встроенный в образ ядра. Затем он скармливает загрузчику испорченные копии этого модуля: обрезанную, собранную для другой машины, с импортом, которого у ядра нет, без заголовка, с неверным магическим числом и собранную под другой интерфейс ядра. Поэтому smoke-загрузки покрывают и загрузчик ([Гейты: как проверять изменения в nos](/howto/run-the-gates)).
- **После изменений в загрузчике или в объявлениях `ffi`** запускайте `scripts/sshd-test.py`.
- **Чтобы проверить модули на неопределённое поведение,** соберите `make nocheck RUSTUB=1`. Модули пересоберутся с проверками переполнения и с проверками предусловий unsafe-операций в `core`. Первое же нарушение станет паникой, которая укажет место.
- **Свой модуль** проверяйте вручную. Если он может сломаться так, что это будет выглядеть как успех, напишите для него собственный гейт: у `netload`, например, есть `scripts/netload-test.py`.

## Если что-то пошло не так

**`make modules` не собирает ваш модуль.** Его имени нет в `MODULES` в `Makefile`.

**Cargo пишет, что пакет `mod-greet` не найден.** Крейта нет в `members` рабочего пространства, или пакет назван не `mod-<name>`.

**`insmod` пишет `init failed`.** Найдите в `dmesg` строку `module init failed`. Частая причина — имя команды: `register` не сработает, если это имя уже занято встроенной командой или командой другого модуля.

**`rmmod` вернулся, а `lsmod` всё ещё показывает модуль как выгружающийся.** Ещё работает одна из его команд, и выгрузка ждёт её завершения. Если команда не завершается никогда, модуль так и останется выгружающимся.

**Ядро запаниковало в вашем коде.** Паника в модуле — это паника ядра. В трассировке ваши кадры помечены `[greet]`.
