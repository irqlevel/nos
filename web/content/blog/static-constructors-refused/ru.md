В обычной программе на C++ часть кода выполняется ещё до `main`. C runtime обходит секцию `.init_array` и вызывает конструкторы всех глобальных объектов, которым они нужны. У ядра C runtime нет. nos запускается из GRUB по Multiboot2 или по протоколу Linux `Image`. Из ассемблерной точки входа ядро сразу попадает в C++ (в `Main` на x86-64 и в `MainArm64` на arm64), и на этом пути `.init_array` никто не обходит.

Пока ни одному глобальному объекту это не нужно, вреда нет. Если у типа глобального объекта `constexpr`-конструктор и тривиальный деструктор, объект инициализируется константно: его байты вычисляет компилятор, и они уже лежат в образе, который грузит загрузчик. Если же конструктор не является константным выражением, инициализация будет динамической. Так бывает, например, когда конструктор определён в другом файле или делает настоящую работу. Тогда компилятор генерирует маленькую функцию, которая вызывает конструктор, и кладёт указатель на неё в `.init_array`.

В nos эту функцию никто не вызывает. Объект остаётся таким, каким его оставил образ: нулями в `.bss`. Ни сбоя, ни предупреждения, ни строчки в логе. И очень часто нули — ровно то, что построил бы конструктор.

## Верно по совпадению

Правило на этот счёт в проекте уже было. С февраля 2026 года соглашения проекта гласили «Static constructors are unreliable in freestanding» и предлагали вместо этого синглтон, который явно создаётся при загрузке. Но соблюдение правила никто не проверял, и ядро уже однажды наступило на эти грабли.

Каждый вторичный процессор (AP) крутится на счётчике, пока загрузочный процессор (BSP) не включит вытеснение. С 2018 года этот счётчик был объявлен как `Atomic PreemptOnWaiting(1);` ([9bf8fcb](https://github.com/irqlevel/nos/commit/9bf8fcb)). Конструктор `Atomic` был определён вне класса, поэтому счётчик начинал с 0, а не с 1, и барьер ни разу не работал так, как написан. На ревью в июле 2026 года барьер переписали на счётчик, который и так начинается с нуля ([fc5b154](https://github.com/irqlevel/nos/commit/fc5b154)), и оставили комментарий с объяснением: «this kernel runs no .init_array, so a dynamically initialized `Atomic x(1)` would in fact be left at 0».

Остальные случаи нашлись случайно. 19 сентября у C++-кода появилась сборка с UBSan, санитайзером неопределённого поведения из clang ([e66e67c](https://github.com/irqlevel/nos/commit/e66e67c)). В её списке секций записи в `.init_array` нашлись у шести слинкованных файлов на x86-64 и у семи на arm64: `pci`, `msix` (на arm64 — `msix_its`), `interrupt_stats`, `sched`, `preempt`, `rust_ffi` и, только на arm64, `pl011`. Большинство из них были верны по совпадению. Несконструированный `Atomic` или `RawRwSpinLock` состоит из одних нулей, а их конструкторы построили бы то же самое.

## Неверно и незаметно

Два других — нет. Это спинлок конфигурационного пространства в `Pci` и `Pl011::OutLock`, спинлок вывода консоли на arm64. Оба имеют тип `RawSpinLock`, а конструктор `RawSpinLock` делает настоящую работу: регистрирует спинлок в watchdog блокировок ([raw_spin_lock.cpp](https://github.com/irqlevel/nos/blob/master/src/cpp/kernel/raw_spin_lock.cpp)).

```cpp
RawSpinLock::RawSpinLock(bool watched)
    : Watched(watched)
    , PreemptTask(nullptr)
    , WatchdogReported(0)
    , WatchdogLockTime(0)
{
    if (Watched)
        Watchdog::GetInstance().RegisterSpinLock(*this);
}
```

Если объект остался нулями, `Watched` равен `false`. Как блокировка такой спинлок работает прекрасно: `Value`, равный 0, означает «свободно». Но ни в одном списке watchdog его нет, и при захвате время не записывается. Watchdog сообщает о любой наблюдаемой блокировке, которую держат дольше 25 мс, и паникует через десять секунд. Этих двух он не видел.

Первый спинлок защищает каждое обращение к конфигурационному пространству PCI, включая обращения Rust-драйверов после запуска SMP. Через второй проходит каждая строка, напечатанная в последовательную консоль arm64. Именно такие блокировки и подвешивают машину, и как раз для них watchdog был слеп.

Хуже всего то, как они сломались. В июле 2026 года, когда оба объекта появились, они были безвредны: конструктор `RawSpinLock` тогда был пустым и дал бы те же нули. Сломались они 4 сентября, когда после дедлока на EX44 в этот конструктор перенесли инструментирование watchdog ([та история](/blog/no-allocation-under-spinlock)). Изменение было в другом файле, и никакое ревью `pci.cpp` или `pl011.cpp` не могло бы его предвидеть. Глобальный объект с динамической инициализацией — это ставка на то, что конструктор его типа навсегда останется тривиальным.

## Три формы без кода при старте

Исправление ([6f83be8](https://github.com/irqlevel/nos/commit/6f83be8)) переводит каждый глобальный объект в одну из трёх форм, которым при старте не нужен никакой код.

**`constexpr`-конструктор и тривиальный деструктор.** Это для типов, у которых создание сводится к записи значений. Такие конструктор и деструктор получили `Atomic` и `RawRwSpinLock`, и теперь их статические экземпляры инициализирует компилятор ([atomic.h](https://github.com/irqlevel/nos/blob/master/src/cpp/kernel/atomic.h)):

```cpp
    constexpr Atomic()
        : Value(0)
    {
    }

    constexpr Atomic(long value)
        : Value(value)
    {
    }
    // ...
    ~Atomic() = default;
```

**Каждый член инициализирован.** Из `RustIrqSlot` и `RustMsixSlot` состоят таблицы, в которых регистрируются обработчики прерываний со стороны Rust. У части их членов не было инициализатора. Конструктор по умолчанию, который оставляет член неопределённым, не является константным выражением. Поэтому компилятор превратил его в конструктор, который выполняется при старте, причём для таблицы, которая и так была бы нулями:

```cpp
struct RustIrqSlot
{
    void (*Handler)(void*) = nullptr;
    void* Ctx = nullptr;
    u8 Vector = 0;
    bool Used = false;
    Kernel::Atomic InFlight; /* ISRs currently executing Handler */
};
```

**Статическая переменная внутри функции.** Это для объекта, конструктор которого действительно должен что-то сделать. Оба спинлока теперь создаются при первом использовании ([pci.cpp](https://github.com/irqlevel/nos/blob/master/src/cpp/drivers/pci.cpp), [pl011.cpp](https://github.com/irqlevel/nos/blob/master/src/cpp/arch/arm64/pl011.cpp)):

```cpp
Kernel::RawSpinLock& ConfigLock()
{
    static Kernel::RawSpinLock lock;
    return lock;
}
```

Первое использование компилятор защищает вызовом `__cxa_guard_acquire`. В nos эта функция выключает вытеснение и прерывания и только потом захватывает атомарный бит ([icxxabi.cpp](https://github.com/irqlevel/nos/blob/master/src/cpp/kernel/icxxabi.cpp)). Поэтому если два CPU наперегонки придут к первому обращению к PCI, спинлок всё равно будет создан один раз.

Мы перечитали изменение и с другой стороны: что может сломать новая форма. Создание спинлока консоли ничего не печатает, потому что не печатают ни конструктор watchdog, ни `RegisterSpinLock`. Значит, первая напечатанная строка не может рекурсивно войти в создание собственного спинлока. А `Panic` пишет по пути, который вообще не берёт блокировок. После исправления команда `watchdog` на arm64 насчитала 816 наблюдаемых блокировок вместо прежних 814, в той же точке той же загрузки.

От одного короткого пути мы отказались. Флаг `-fno-c++-static-destructors` одним махом убрал бы из `.init_array` регистрацию деструкторов. Но nos при выключении вызывает `__cxa_finalize`, и деструкторы синглтонов там кое-что проверяют. Например, деструктор `BlockAllocatorImpl` ищет утечки. Поэтому требование, наоборот, стало строже: глобальному объекту нужен не только `constexpr`-конструктор, но и тривиальный деструктор.

## Линковка, которая их не пропустит

Само по себе ничего из этого исправленным бы не осталось. Правило было записано ещё в феврале, а оба спинлока появились уже после него. Поэтому оба скрипта линкера теперь собирают все секции конструкторов и деструкторов в секцию `INFO`, которая никогда не загружается в память, и проверяют, что она пуста ([linker-arm64.ld](https://github.com/irqlevel/nos/blob/master/build/linker-arm64.ld)):

```diff
+    .static_init (INFO) : {
+        *(.preinit_array)
+        *(.init_array) *(.init_array.*)
+        *(.ctors) *(.ctors.*)
+        *(.fini_array) *(.fini_array.*)
+        *(.dtors) *(.dtors.*)
+    }
+    ASSERT(SIZEOF(.static_init) == 0, "a static constructor or destructor: this kernel runs none (CLAUDE.md)")
```

Теперь глобальный объект, которому нужен код при старте, роняет сборку, а не тихо остаётся нулями. Мы проверили это напрямую: добавили глобальный `RawSpinLock`. Обе линковки, GNU ld для x86-64 и ld.lld для arm64, упали с этим сообщением. Проверка видит каждый объектный файл, попадающий в образ, на каком бы языке он ни был написан, и ничего не стоит во время работы.

Вместе с этим изменилось правило в CLAUDE.md, файле с соглашениями проекта. Было «Static constructors are unreliable», стало «Static constructors do not run, and the link refuses one» ([сборка](/docs/build#four-things-the-makefile-will-not-tell-you)). Разница между этими двумя фразами и есть смысл всей затеи. Первая — совет, и помнить о нём должен тот, кто напишет следующий глобальный объект. Вторая — свойство сборки, и сборка помнит за него. Когда ошибка возможна только потому, что кто-то забыл правило, мы ищем место, где забытое правило остановит сборку. Это может быть тип, тестовый гейт или, как здесь, несколько строк скрипта линкера ([цель проекта](/about)).
