EX44 перестал отвечать. Это один из двух серверов Hetzner, на которых работает nos, и его единственная консоль — сеть: команды мы вводим через [UDP-шелл](/docs/udp-shell), а лог читаем через [netconsole](/docs/netconsole). Мы вводили в шелле `ps`, и третий вызов остался без ответа. В следующий раз завис седьмой. Не было ни паники, ни исключения. Лог netconsole просто обрывался на полуслове, и машину ничто не перезагрузило: ничего не сломалось так, чтобы ядро умело это заметить.

## Два стека вызовов

Воспроизвести зависание удалось на гостевой машине QEMU с 20 CPU. Мы запускали `ps` по UDP-шеллу в цикле, и где-то между 60-й и 140-й итерацией всё вставало. Мы подключили GDB к gdbstub в QEMU, и вся история уместилась в стеки двух CPU. Вот они в том виде, в каком их записал коммит с исправлением:

```text
CPU#0  UdpShell::Run -> SendUdp -> SendRaw -> NetDevice::SubmitTx
       -> RawSpinLock::LockIrqSave(TxQueueLock)          spinning, IRQs off

CPU#1  softirq -> VirtioNet::DrainTx (holds TxQueueLock) -> CompleteTx
       -> NetFrame::Put -> Mm::Free -> PageAllocator::Free
       -> CpuTable::InvalidateTlbRange -> SendTlbIPI(mask 0xFFFFD)
       -> WaitGroup::Wait                                waiting for CPU#0
```

CPU#1 завершал обработку отправленных кадров и при этом держал TX-лок устройства. Когда исчезала последняя ссылка на кадр, кадр освобождался, а при освобождении снималось отображение страницы. На x86 `invlpg` чистит только локальный TLB. Поэтому `CpuTable::InvalidateTlbRange` рассылает всем остальным работающим CPU межпроцессорное прерывание (IPI) с просьбой выбросить устаревшую трансляцию и ждёт, пока каждый подтвердит ([страничная память](/docs/paging#tlb-shootdown-and-the-deadlock-it-can-cause)).

Маска `0xFFFFD` означает все CPU, кроме отправителя, в том числе CPU#0. А CPU#0 крутился на том же TX-локе, который `LockIrqSave` берёт с выключенными прерываниями, поэтому IPI он так и не принял. CPU#1 ждал CPU#0, а CPU#0 ждал лок, который держал CPU#1. Остальные восемнадцать процессоров ответили и ушли в idle.

Исключения не было, поэтому не было и паники. Аппаратный TCO watchdog чипсета не был взведён, так что никто не перезагрузил машину. А задаче, которая отправляет лог netconsole, нужен был тот же TX-лок, чтобы отправить хотя бы одну строку. Поэтому лог и обрывался на полуслове.

Обиднее всего, что эта опасность уже была описана, причём в том же самом драйвере. Его обработчик прерывания откладывал завершение TX в softirq именно потому, что «Mm::Free() can trigger a TLB shootdown IPI [and] if another CPU has IRQs disabled the IPI cannot be acknowledged, causing a deadlock». Отложить было необходимо, но недостаточно. Потом softirq брал TX-лок с выключенными прерываниями и всё равно освобождал кадры под ним. Проблема никогда не была в прерываниях на освобождающем CPU. Она была в прерываниях на том CPU, который крутится на локе.

## Собрать, отпустить, освободить

Исправление ([eaff359](https://github.com/irqlevel/nos/commit/eaff359)) задало форму, которая потом повторялась в каждом следующем случае. Под локом переложить всё, что нужно освободить, в локальный список. Отпустить лок. И только потом освободить.

```cpp
void VirtioNet::DrainTx()
{
    Stdlib::ListEntry done;
    done.Init();

    ulong flags = TxQueueLock.LockIrqSave();
    CompleteTx(done);
    FlushTx();
    TxQueueLock.UnlockIrqRestore(flags);

    // ...
    while (!done.IsEmpty())
    {
        NetFrame* frame = CONTAINING_RECORD(done.RemoveHead(), NetFrame, Link);
        frame->Put();
    }
}
```

После этого сценарий прошёл 800 прогонов. Ничего специфически сетевого в правиле нет, поэтому оно попало в CLAUDE.md: никогда не выделять и не освобождать память, держа спинлок. На arm64 именно этот цикл замкнуться не может. Там `TLBI` рассылается аппаратно, `Hal::TlbShootdownNeedsIpi()` возвращает false, и никто никого не ждёт. Но код у обеих архитектур общий, а все три реальные машины, на которых работает nos, — это x86-64.

## Не тот драйвер

Через шестнадцать минут пришла поправка ([fc314e7](https://github.com/irqlevel/nos/commit/fc314e7)). Сценарий гоняли на virtio-net, потому что именно его даёт QEMU. А в EX44 стоит RTL8125. Его Rust-драйвер, как и драйвер r8168, разбирал TX-кольцо прямо в `flush_tx`, который сетевой стек вызывал под тем же TX-локом, и там же делал `drop` каждому отправленному кадру. Это был тот же дедлок, причём на той самой машине, где он и случался.

Мы утверждали, что остальные драйверы проверены. Но grep, на котором держалось это утверждение, искал имя функции, которого в дереве нет. Он ничего не нашёл, и это «ничего» мы приняли за «чисто».

Поэтому мы перенесли освобождение из драйверов в слой, которому принадлежит лок: там драйвер ошибиться не может. Сегодня сетевой слой написан на Rust. `flush_tx` драйвера на время вызова получает `TxQueue` взаймы, и у готового кадра есть один задокументированный выход ([device.rs](https://github.com/irqlevel/nos/blob/master/src/rust/net/src/device.rs)):

```rust
/// A transmitted frame, for release once the lock is down. Never dropped
/// here instead: dropping frees, a free can reach the page allocator,
/// which shoots down the TLB on every other CPU and waits for each -- and
/// a CPU spinning on this lock has interrupts off and never answers.
pub fn done(&mut self, frame: Frame) {
    self.done.push(frame);
}
```

Эту очередь слой разбирает уже после того, как отпустил лок:

```rust
pub fn release_tx_done(&self) {
    loop {
        let frame = self.tx.lock().done.pop();
        match frame {
            /* Outside the lock, always: see `tx_done` */
            Some(frame) => drop(frame),
            None => return,
        }
    }
}
```

`self.tx` — это `IrqSpinLock<Tx>`, лок, который владеет защищаемыми данными ([sync.rs](https://github.com/irqlevel/nos/blob/master/src/rust/kcore/src/sync.rs)). До очереди нельзя добраться иначе как через guard этого лока, и следит за этим тип, а не комментарий. Guard, который здесь возвращает `lock()`, временный: он уничтожается в конце `let`. Поэтому к моменту `drop(frame)` лок уже отпущен. В `submit_tx` есть ещё одна тонкость: он освобождает кадры, только если прерывания включены. Вызывающий код с выключенными прерываниями сам не смог бы ответить на shootdown, поэтому он поднимает TX softirq и оставляет освобождение ему.

## Десять секунд, потом отчёт

Правило в файле остановит следующий случай, только если его кто-то прочтёт, а мы только что показали, как легко такой случай пропустить. Поэтому тот же коммит сделал сбой громким. Раньше ожидание подтверждений было циклом, который мог закончиться только ответом. Теперь `CpuTable::SendTlbIPI` сдаётся через десять секунд, что намного дольше любого нормального раунда IPI, и паникует, перечисляя CPU, которые так и не ответили ([cpu.cpp](https://github.com/irqlevel/nos/blob/master/src/cpp/kernel/cpu.cpp)):

```cpp
    static const ulong AckTimeoutNs = 10 * Const::NanoSecsInSec;
    // ...
    for (ulong i = 0; i < MaxCpus; i++)
    {
        // ...
        while (tasks[i].Completion.GetCounter() != 0)
        {
            if (GetBootTime() >= deadline)
            {
                silent |= (1UL << i);
                break;
            }

            YieldToRunnable();
        }
    }

    if (silent != 0)
        Panic("TLB shootdown: cpus 0x%lX never acknowledged (asked 0x%lX)",
            silent, cpuMask);
```

Позже в тот же день этот урок усвоил и watchdog локов ([22e49c2](https://github.com/irqlevel/nos/commit/22e49c2)). Он следил только за `SpinLock`, а `TxQueueLock` был `RawSpinLock`. Поэтому `dmesg 2048 Spinlock` ничего не показывал на машине, где TX-лок держали минутами. Проверки переехали в `RawSpinLock`, и лок, который держат десять секунд, теперь вызывает панику, а не очередную строку в трассе.

Ещё путь паники научился отправлять отчёт без TX-лока. Он пробует взять лок один раз и, если не вышло, идёт дальше без него. Иначе отчёту пришлось бы выходить через ту самую заклинившую дверь. Потом мы нарочно повесили машину командой шелла, которая навсегда захватывает TX-лок с выключенными прерываниями. Отчёт дошёл до коллектора логов в таком виде:

```text
Spinlock 0xFFFF800040420330 is held too long 27055333
PANIC: Spinlock 0xFFFF800040420330 stuck, held 10003951083 ns
CPU: 3  Task: pid 3 name idle3
Backtrace: DoPanic <- Watchdog::Check <- GenericTimer::LocalTick <- ArmIrqEntry
```

## Путь данных, который ничего не освобождает

Освобождать вне лока хорошо, а ещё лучше вообще не возвращать память аллокатору. В тот же день, 4 сентября ([c3e1d8d](https://github.com/irqlevel/nos/commit/c3e1d8d)), сетевые кадры переехали в пул, который строится один раз при загрузке. Кадры в нём фиксированного размера, а их физические адреса вычисляются один раз. Раздаются кадры из кэшей на каждом CPU, и эти кэши трогают только с выключенными прерываниями и без атомарных операций. За кэшами стоит одно кольцо без блокировок: ограниченная MPMC-очередь Вьюкова (с несколькими производителями и потребителями). Кэши пополняются из него и сбрасывают в него излишки пачками по 32.

Коммит прямо называет приоритет: путь данных, который никогда не зовёт аллокатор, этой ошибки иметь не может вовсе, и это ценнее скорости. На гостевой arm64-машине с 4 CPU за 500 обменов с шеллом из пула ушло 506 кадров без единого промаха, а к кольцу обратились 31 раз. Теперь пул написан на Rust ([frame.rs](https://github.com/irqlevel/nos/blob/master/src/rust/net/src/frame.rs)). По умолчанию в нём 4096 кадров. Изменить это можно параметром `netframes=`, а посмотреть состояние пула — командой `netpool`.

А скорость пришла сама собой. На AX41 первый флуд после каждой загрузки терял кадры прямо на сетевой карте: 755 105 из 2,06 миллиона, и все за первые две секунды. Приёмное кольцо заполнялось через `Mm::Alloc` ещё до того, как поднимался пул. Каждое освобождение такого кадра запускало TLB shootdown, который ждал ответа от всех остальных CPU, а на этой машине это около 4 мс на кадр ([e02dfe3](https://github.com/irqlevel/nos/commit/e02dfe3)). Теперь пул поднимается раньше любого драйвера.

## Правило как автоматическая проверка

Фаззеры ([тесты и гейты](/docs/testing)) проверяют это правило автоматически. Аллокатор, на котором работают сетевой и дисковый фаззеры, проверяет каждое выделение и каждое освобождение. Выделение или освобождение с выключенными прерываниями считается находкой. Фаззер указывает строку, где оно случилось, и сообщает seed и номер итерации, которые его воспроизводят. Паника объясняет почему: «a spin lock held: a free can wait on every other CPU, and one spinning on this lock never answers» ([heap.rs](https://github.com/irqlevel/nos/blob/master/fuzz/common/machine/heap.rs)). Цель heap в C++-фаззере требует того же для каждой страницы, которую берёт аллокатор: `INVARIANT(Fuzz::HeldSpinLocks() == 0, "a page allocated with a spin lock held")`.

30 сентября C++-фаззер нашёл нарушение там, где мы стали бы искать в последнюю очередь: в самой куче ядра ([00631ab](https://github.com/irqlevel/nos/commit/00631ab)). `Pool::Alloc`, через который проходят мелкие выделения кучи, брал новую страницу у страничного аллокатора, держа собственный спинлок пула. Если отобразить эту страницу не удавалось, страничный аллокатор сбрасывал TLB на всех CPU и ждал. А CPU, который крутится на локе пула, не ответил бы никогда. Исправление снова той же формы. Страница выделяется уже после того, как лок отпущен. Если другой CPU тем временем положил страницу в список, лишняя возвращается, тоже вне лока ([pool.cpp](https://github.com/irqlevel/nos/blob/master/src/cpp/mm/pool.cpp)):

```cpp
    if (block == nullptr)
    {
        Page* page = NewPage();
        if (page == nullptr)
            return nullptr;

        Page* spare = nullptr;
        {
            Stdlib::AutoLock lock(Lock);

            if (FreePageList.IsEmpty())
            {
                FreePageList.InsertHead(&page->Link);
                EmptyPages++;
            }
            else
                spare = page;
            block = TakeLocked();
        }

        if (spare != nullptr)
            PgAlloc->Free(spare);
    }
```

Этот класс ошибок никуда не делся, и ядро не делает вид, будто его нет. Изменилось другое: такие ошибки больше не проходят молча. Правило в CLAUDE.md их называет. На пути передачи сетевой слой даёт драйверу один способ вернуть кадр. Фаззеры ловят нарушение в той строке, где оно случилось. Пул кадров держит самый нагруженный путь подальше от аллокатора. А на реальной машине новый случай через десять секунд превращается в панику, которая приходит по netconsole с номерами не ответивших CPU, а не в сервер, который просто встал.

У EX44 в запасе было ещё одно тихое зависание, на этот раз на приёме. Его исправили на следующий день, и это [отдельная история](/blog/rtl8125-lost-msix-edge).
