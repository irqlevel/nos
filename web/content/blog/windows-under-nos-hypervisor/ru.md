Первая полезная загрузка Windows на nos началась вовсе не с установщика Windows. Она началась с образа прошивки размером 4 МиБ, процессорного регистра, который останавливал прошивку ещё до первой напечатанной строки, и последовательной консоли.

Сегодня подготовленный образ Windows Server 2022 Standard Core загружается под `hv.ko` до Special Administration Console (SAC) примерно за 1,7 секунды на Intel EX44. Драйвер virtio-диска работает, сетевой интерфейс получает адрес по DHCP, а ping доходит до nos. Можно открыть канал CMD, сохранить и восстановить работающую ВМ, а затем выполнить `shutdown /s /t 0` вместо аварийного снятия питания. Через `hv forward` проходит и RDP-согласование Hybrid/NLA — после разрешения TCP 3389 в брандмауэре гостя.

Это практический результат, но ещё не обещание, что любая версия Windows устанавливается и работает на nos. Сейчас поддерживается запуск Windows Server из подготовленного образа, в который уже установлен virtio-win. Установка с ISO внутри nos, графическая консоль, постоянные переменные UEFI, Secure Boot и TPM ещё впереди. Ниже — история того, как мы дошли до текущего состояния, включая то, что сначала не заработало.

## W0: сначала прошивка, потом Windows

Существующий путь загрузки Linux умел либо стартовать ядро напрямую, либо запускать небольшую программу `hvboot`, которая читает собственный `/boot` облачного образа. Для установочного диска Windows ни то ни другое не подходит. Windows ждёт платформу PC и прошивку UEFI, поэтому мы решили запускать сборку OVMF `CloudHv` из EDK2 как PVH-гостя. Cloud Hypervisor уже пользуется таким путём, а наш существующий PVH-загрузчик позволял подать прошивку гостю без второго механизма загрузки.

W0 оказался семью частями работы над платформой:

| Шаг | Что появилось |
|---|---|
| W0.1 | Воспроизводимые сборки прошивки RELEASE и DEBUG из зафиксированных исходников EDK2, лицензии и упаковка в системный образ |
| W0.2 | Q35 для обычных гостей и отдельная машина, которую ждёт прошивка CloudHv |
| W0.3 | Фиксированные и переменные MTRR на каждый vCPU, включая `MTRR_DEF_TYPE`, состояние после сброса и правила исключений |
| W0.4 | MSI-X BAR устройств virtio, которые прошивка может перемещать без потери backing-памяти хоста и состояния миграции |
| W0.5 | Параметр `firmware` в командах и `vm.toml`, сохранение, восстановление и миграционное состояние прошивки |
| W0.6 | Запуск на настоящем VT-x, UEFI Shell и загрузка Ubuntu через собственные shim и GRUB |
| W0.7 | Постоянный UEFI-гейт: Boot Manager, набранная в Shell команда и save/restore работающей ВМ с прошивкой |

Сборка прошивки привязана к `edk2-stable202608`. В ней нет SMM, TPM, Secure Boot и сетевого стека iSCSI, зато есть UEFI Shell. `scripts/build-cloudhv.sh --check` заново собирает RELEASE-образ и сравнивает его побайтово. Во время ежедневной отладки это было важно: странное поведение прошивки можно было исследовать по исходникам, а не подозревать неизвестно как полученный бинарник.

Заодно обычные гости перешли на Q35. Они получили современную PCI-машину с ECAM на 256 шин. CloudHv намеренно устроен иначе: он узнаёт свою платформу по device ID host bridge `0x0D57`, пользуется CF8/CFC вместо ECAM и ждёт, что нижняя RAM закончится не выше `0xC0000000`. Один общий переключатель «UEFI-машина» спрятал бы эти различия за флагом. У нас обе раскладки явно описаны в модели машины.

### Отказы до первого Shell

Фаза SEC прошивки пишет в `MTRR_DEF_TYPE` до того, как у неё появляется консоль. Без поддержки MTRR запись вызывала `#GP`, и гость просто останавливался. Прочитать сообщение прошивки было нельзя: код, который мог его напечатать, ещё не выполнялся.

Затем прошивка занялась своей обычной работой: обошла PCI и начала перемещать BAR. Таблица MSI-X устройства virtio находится в memory BAR, но хост не может просто перейти по адресу, выбранному гостем. Для эмуляции устройства и сохранённого состояния таблица имеет постоянную backing-память хоста, а отображение во вложенной таблице страниц следует за BAR гостя. Недопустимый адрес оставляет его неотображённым. У перемещения во время съёмки dirty log есть отдельные правила, а попытка сохранить ВМ в середине измерения размера BAR отклоняется, чтобы не записать в состояние выдуманную конфигурацию.

Прошивка также делала куда более крупные дисковые запросы, чем наши Linux-гости. EDK2 выдавал чтения на 896 КиБ одним virtio-дескриптором. Блочный backend работает кусками по 256 КиБ, поэтому hv теперь обслуживает такой запрос по частям и пишет один финальный статус после завершения всего запроса. Ошибка в поздней части тоже должна завершить запрос гостя ровно один раз. Теперь фаззер проверяет и эти случаи, и успешное разбиение.

Результатом был ещё не Windows, но кое-что более полезное для его отладки: DEBUG-прошивка доходила до `Shell>` и выполняла команды на настоящем Intel VT-x, а RELEASE загружала собственные shim и GRUB Ubuntu 24.04 вплоть до входа в Linux, который видит EFI.

## W1: Windows ждёт сервисы Hyper-V

Для загрузки Windows оказалось мало UEFI и драйверов virtio. Windows рассчитывает на таймеры и доставку прерываний, которых в нашей минимальной прошивочной машине иначе не было. В частности, без синтетических таймеров Hyper-V она ждёт HPET или периодические прерывания RTC. Вместо очередного набора старых устройств мы реализовали документированный интерфейс Hyper-V, который Windows уже умеет использовать.

Параметр `hyperv` у firmware-гостя даёт ему CPUID-интерфейс `Hv#1`, MSR guest OS и hypercall, доступную только для чтения страницу гипервызовов, индексы vCPU, reference TSC page и счётчик reference time. Страница часов использует документированный sequence-протокол, чтобы гость никогда не прочитал наполовину обновлённое время.

У каждого vCPU есть состояние SynIC и четыре синтетических таймера. Таймер может доставлять непосредственно вектор прерывания или сообщение SynIC, срабатывать один раз или периодически и будить vCPU даже из halted-состояния. Это не просто хост-таймеры, после которых хост вспоминает про прерывание гостя: их сроки — часть состояния прерываний vCPU и участвуют в save/restore.

Область гипервызовов намеренно узкая. Неизвестный или неправильно сформированный вызов получает определённый статус Hyper-V, а не сквозной доступ к хосту. Crash MSR P0–P4 и CrashNotify тоже сохраняются, поэтому bugcheck Windows оставляет после себя нечто более полезное, чем остановившуюся консоль.

### Три загрузки, три разные причины

Последний участок пути до SAC ещё раз напомнил, что «Windows не грузится» — не диагноз.

Один отказ на VT-x возник из-за взаимодействия TPR threshold эмулируемого APIC с процессорным interrupt-window control. VM entry отклонялся до того, как Windows могла продвинуться дальше. После исправления мы оставили диагностику: теперь отказ входа сохраняет соответствующие VMCS controls, invalid bits, состояние MSR-load и прерываний в дампе остановленного vCPU. Следующий такой отказ не придётся восстанавливать по одному номеру ошибки.

Другой проблемой оказался ACPI. Сначала firmware-машина имела legacy FADT, тогда как CloudHv и Windows используют hardware-reduced ACPI. Теперь FADT прошивки описывает настоящие sleep-control/status-регистры и не содержит старых PM1-блоков. DSDT также описывает процессоры, COM1 и ресурсы, которые действительно видит Windows.

Третья загрузка застряла в цикле опроса RTC. Бит update-in-progress был всегда сброшен. На первый взгляд это удобно: часы всегда безопасно читать. Но драйвер, который ждёт завершения цикла обновления, вполне обоснованно может ждать вечно, если цикла не бывает никогда. Теперь RTC ведёт себя как часы, а не как очень вежливая константа.

Была и ошибка вне гипервизора. Сценарий автоматической подготовки образа использовал DISM с `/Add-Driver` и `/Online`, хотя `/Add-Driver` работает только с offline-образом. В результате в образе не оказалось работающего viostor. Теперь сценарий ставит virtio-win командой `pnputil /add-driver ... /install`. Сначала мы проверили образ с системным диском на virtio под QEMU, отделив ошибки подготовки от ошибок hv, и только потом запустили его под nos.

После этого последовательная консоль дошла до SAC. Канал CMD принял вход Administrator, viostor работал, NetKVM получил `10.0.100.4/24`, а ping дошёл до `10.0.100.1`. На EX44 первая Windows-ВМ добралась до SAC примерно за 1,65 секунды.

### Штатное выключение — тоже тест модели устройств

При корректном выключении Windows вскрылся один из наших любимых небольших фактов об этом проекте. Windows доходит до UEFI `ResetSystem(EfiResetShutdown)`. Runtime CloudHv реализует этот вызов записью байта `0x34` в фиксированный sleep-control порт `0x600`.

У legacy Q35 тоже есть регистр по адресу `0x600`, но там это PM1 status, а не hardware-reduced sleep control. Поэтому внешне одинаковая запись должна выключать одну машину и не выключать другую. PM-фаззер теперь проверяет обе трактовки. Работающий `shutdown /s /t 0` — не просто удобство: он показывает, что прошивка, ACPI, модель устройства и гость согласны друг с другом по поводу того, что за машина под ними находится.

На этом этапе мы также сохранили работающую Windows-ВМ — в том прогоне записалось 679 МиБ, а пауза заняла 5,9 секунды, — восстановили её, снова проверили CMD и ping, а затем позволили Windows выключиться самой. UEFI save/restore-гейт прошёл на настоящих AMD-V и Intel VT-x, а также под TCG.

## W2: меньше выходов, а не больше хитростей

Windows загружалась, но простаивающая ВМ была занята не тем, чем хотелось бы. VM exit — это переход из гостя обратно в гипервизор. Эмулировать регистр или прерывание через такой переход куда дороже, чем позволить vCPU продолжить работу.

До оптимизации мы измерили окно простоя длиной примерно 2,666 секунды. В нём было 1657 выходов. Из них 1163 приходились на nested-page fault страницы xAPIC; хост видел 479 записей EOI и 665 обращений к ICR. Так появились три конкретных места для работы: завершение прерывания, межпроцессорные прерывания и сброс TLB.

Сопоставимое окно после оптимизации длилось столько же:

| Измерение простоя Windows | До | После |
|---|---:|---:|
| Всего VM exits | 1657 | 647 |
| Nested-page faults xAPIC | 1163 | 0 |
| Записи EOI, увиденные хостом | 479 | 1 |

Первый механизм — виртуальный APIC-интерфейс Hyper-V: MSR EOI, ICR и TPR, а также VP-assist page на каждый vCPU. VP-assist позволяет отметить прерывание как не требующее EOI. Если гость сбрасывает это состояние, а EOI всё же остаётся долгом, hv завершает его на следующем выходе. SynIC AutoEOI обрабатывается при внедрении прерывания. Когда AutoEOI настроен, hv отключает APIC virtualization для такого случая, а не предполагает, что две оптимизации прерываний автоматически безопасно сложатся друг с другом.

В отдельном измерении VP-assist сократил число EOI-выходов с 497 до 8.

Второй механизм — synthetic ICR. Удалённый fixed IPI теперь попадает в существующий быстрый путь world switch вместо более длинного общего пути обработки выхода. Hypercall synthetic cluster IPI поддерживает простые 64-битные VP-маски в memory- и fast-формах. Медианное время обработки synthetic ICR на хосте сократилось с 2,2 микросекунды до 715 наносекунд.

Третья часть — инвалидация TLB. `HvFlushVirtualAddressSpace` и `HvFlushVirtualAddressList` сразу отмечают сброс на вызвавшем vCPU, а остальным отправляют атомарный запрос и doorbell. Удалённый vCPU обрабатывает запрос перед следующим VM entry. VMX использует инвалидацию VPID, SVM забывает затронутый ASID. List flush пока консервативно сбрасывает весь TLB. Простые flush поддерживают memory- и fast register/XMM-формы; sparse Ex-формы не объявляются.

Одной из неверных теорий было предположение, что Windows нужно ждать подтверждения каждого удалённого сброса TLB. Добавление ожидания не исправило сбой. Настоящая причина оказалась в control flags гипервызова. Мы исправили их проверку и убрали лишнюю сериализацию, а не оставили замедление, которое ничего не решило.

Финальный прогон Windows сообщил о 3196 гипервызовах — 3195 сбросах TLB и одном synthetic IPI — без ошибок и таймаутов flush. Восстановленная ВМ снова ответила через CMD и ping, а затем штатно выключилась.

## Какие проверки остаются после отладки

Одна успешная загрузка — плохой регрессионный тест, если её след остался только в прокрутке терминала. Фаза прошивки теперь входит в каждый x86-64 `hv-test.py`: CloudHv доходит до Boot Manager и UEFI Shell, выполняет набранную команду, сохраняет и восстанавливает работающую firmware-ВМ, а затем выполняет ещё одну команду после восстановления.

Политика Hyper-V CPUID и MSR, reference clock, SynIC, таймеры, VP-assist, APIC-интерфейс и форматы vmstate покрыты фаззингом. Whole-machine target прогоняет правильные flush- и IPI-гипервызовы через настоящий цикл исполнения. Мутационные проверки нарочно убирают отдельные условия и требуют, чтобы какой-нибудь target это заметил. Финальный W2-прогон фаззера охватил 2 250 000 входов без находок.

Обычные `make check`, сборки и smoke-тесты x86-64 и arm64 остались зелёными. Так же прошли x86-тест гипервизора под TCG и на настоящем AMD-V. Сама Windows остаётся ручным гейтом на EX44, потому что её образ нельзя распространять вместе с репозиторием.

Полный [план Windows](https://github.com/irqlevel/nos/blob/master/plans/windows.md) содержит измерения и отдельные шаги W0–W2. Основная реализация вошла коммитом [8b3e536a](https://github.com/irqlevel/nos/commit/8b3e536a2dae2231aae94dfac77285ab9f84c36c), следом — [оптимизации W2](https://github.com/irqlevel/nos/commit/75d8809b90f924899eced4c91d1c37fa6cecc706).

## Что уже работает, а чего ещё нет

Текущую границу лучше назвать прямо.

**Уже работает:**

- Windows Server 2022 Standard Core из подготовленного образа с установленным virtio-win.
- Загрузка UEFI через находящуюся в репозитории прошивку CloudHv, в сборках DEBUG и RELEASE.
- Диски и сеть virtio, DHCP и NAT, SAC/EMS и канал CMD на COM1.
- RDP-согласование через проброшенный TCP-порт после разрешения в брандмауэре гостя.
- Reference time Hyper-V, синтетические таймеры, SynIC, APIC MSR, VP-assist, synthetic IPI и объявленные flush-вызовы.
- Штатное выключение и save/restore работающей ВМ. Формат состояния также несёт данные прошивки и Hyper-V, нужные механизму миграции.

**Ещё не работает:**

- Установка Windows с ISO прямо на nos. W3 требует эмулируемые NVMe-диск, AHCI/ATAPI CD для установки, сетевую карту e1000e и читатели VHD/VHDX. Пока подготовка образа выполняется под QEMU.
- Графическая консоль Windows. W4 требует GOP, framebuffer гостя, VNC/noVNC и подходящие устройства клавиатуры и указателя. SAC — последовательный путь управления; RDP пробрасывается, но сам nos его не отображает.
- Полное соответствие требованиям Windows 11. W5 требует TPM 2.0, Secure Boot и постоянные переменные UEFI. Сейчас переменные живут в RAM и не переживают перезапуск. LabConfig позволяет обойти проверки установщика, но это не то же самое, что поддержка требований платформы.
- Сравнение производительности Windows с KVM на одном и том же образе. Мы измерили улучшение W2 относительно нашей непосредственно предшествующей реализации, а не KVM с этим образом.
- Все возможные вызовы Hyper-V. Sparse Ex-формы flush намеренно не объявляются, а list flush пока инвалидирует весь TLB.

Остаётся и работа над производительностью. Текущий образ Server 2022 по-прежнему работает в режиме xAPIC. Аппаратная виртуализация страницы xAPIC и AMD AVIC могут помочь, но это следующие измерения, а не автоматически следующие функции. Прежние эксперименты с APIC уже показали, что меньшее число выходов не всегда означает более быструю нагрузку.

W0 дал нам прошивку, которой можно доверять. W1 добился от Windows загрузки и штатного выключения. W2 убрал 61% выходов из простаивающей Windows-ВМ. Следующие вехи в меньшей степени про то, как уговорить Windows терпеть нашу машину, и в большей — про установку, консоль и платформу, для которых не понадобится подготовительный ритуал.
