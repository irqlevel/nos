Почти всё, что читает ядро, написал кто-то другой. Гость сам выбирает каждый байт своих virtio-колец, то есть очередей, через которые он общается с виртуальными устройствами. Сеть присылает какие угодно кадры и ответы DHCP. Диск сам сообщает свою геометрию: хоть 520-байтные секторы, хоть 2^64 штук.

Прошивка передаёт дерево устройств, таблицы ACPI и карту памяти ещё до того, как у машины без монитора появится хоть какая-то консоль. Если ядро запаникует на любом из этих путей, машина остановится. А на двух наших серверах в Hetzner, где единственная консоль — сеть, она остановится молча.

Тестовая загрузка под QEMU видит только те входные данные, которые выдаёт сам QEMU. Поэтому в последние два дня сентября 2026 года мы добавили четыре фаззера. Каждый из них превращает настоящий код ядра, а не его копию или модель, в обычную программу, которая работает на хосте: на машине разработчика или в CI.

## Собираем исходники ядра для хоста

Большая часть кода, который нужно было фаззить, уже была переносимой. Блочный, сетевой и файловый слои написаны как Rust-крейты поверх `kcore` и `ffi`, а через эти два крейта Rust обращается к службам ядра ([как слои туда попали](/blog/cpp-to-rust-layers) — отдельная история). Cargo собирает их для хоста так же легко, как для ядра. [`fuzz/fs`](https://github.com/irqlevel/nos/blob/master/fuzz/fs/Cargo.toml) подключает их по пути и использует тот же профиль сборки, что и ядро с `RUSTUB=1`. Поэтому переполнение на хосте вызывает ту же панику, что и в ядре, а не проходит молча:

```toml
[dependencies]
# The kernel's crates, built for the host as they are for the kernel.
ffi = { path = "../../src/rust/ffi" }
kcore = { path = "../../src/rust/kcore" }
block = { path = "../../src/rust/block" }
fs = { path = "../../src/rust/fs" }

# What a RUSTUB=1 kernel has on, in every crate: an overflow is a panic, not
# a wrap, and core's checks of its own unsafe preconditions are made.
[profile.release]
overflow-checks = true
debug-assertions = true
panic = "unwind"
```

С гипервизором сложнее. Его файлы импортируют `hvarch`, крейт, который управляет расширением виртуализации процессора и содержит весь `unsafe`-код гипервизора. Программа на хосте такой код выполнить не может. Поэтому [`fuzz/hv`](https://github.com/irqlevel/nos/blob/master/fuzz/hv/src/main.rs) компилирует файлы гипервизора по одному как свои модули и сам отзывается на имена крейтов `ffi`, `hv`, `hvarch` и `kcore`. Всё, к чему эти файлы обращаются снаружи, от часов до процессора, заменено заглушками в той же программе:

```rust
extern crate alloc;
extern crate self as ffi;
extern crate self as hv;
extern crate self as hvarch;
extern crate self as kcore;
// ...
#[path = "../../../src/rust/hv/src/acpi.rs"]
pub mod acpi;
// ...
/// The guests' DHCP server, from the module: what a guest's DHCP client's
/// frames reach.
#[path = "../../../src/rust/modules/hv/src/dhcp.rs"]
pub mod dhcp;
```

C++ получает то же самое другим путём. [`fuzz/cpp/Makefile`](https://github.com/irqlevel/nos/blob/master/fuzz/cpp/Makefile) компилирует файлы ядра как есть, под ASan и UBSan (санитайзерами адресов и неопределённого поведения). Первым в пути поиска заголовков стоит хостовый HAL (слой абстракции оборудования), который подменяет inline-HAL каждой архитектуры. В нём нет привилегированных инструкций, а хуки MMU видны той цели фаззинга, которая моделирует MMU. Все четыре фаззера лежат в `fuzz/`, а не в `src/rust/`, потому что тамошний `.cargo/config.toml` превращает любую сборку cargo ниже по дереву в сборку ядра.

## Машина, на которой они работают

Сетевому и файловому слоям нужно ядро под ними. [`fuzz/common`](https://github.com/irqlevel/nos/blob/master/fuzz/common/machine/sched.rs), общий для сетевого и файлового фаззеров, и есть такое ядро, написанное специально для этой цели. Каждая задача в нём работает в своём потоке хоста, но в каждый момент выполняется только одна. Когда задача блокируется или отпускает блокировку, следующую задачу выбирает вход.

По настоящим часам никто не спит. Если ждут все задачи, время сразу перескакивает к ближайшему дедлайну, так что час аренды DHCP обходится не дороже срабатывания её таймеров. А правила ядра проверяются прямо в той строке, которая их нарушает:

```rust
pub fn check_may_wait(what: &str) {
    match ctx() {
        Ctx::Softirq => panic!("invariant: a soft IRQ handler {}: every packet waits for it -- the receive path \
                                must never sleep", what),
        Ctx::Irq => panic!("invariant: an interrupt handler {}", what),
        Ctx::Task => {}
    }
    if irq_off() != 0 || preempt_off() != 0 {
        panic!("invariant: task {} {} with a spin lock held or interrupts off (irq {}, preempt {})", me(), what,
               irq_off(), preempt_off());
    }
}
```

Так же ловятся две блокировки, взятые в разном порядке, выделение памяти с выключенными прерываниями и задача, которая завершилась, не отпустив блокировку. Каждый такой случай становится находкой (так фаззеры называют пойманную ошибку) ровно там, где он произошёл. Все входы выполняются в отдельных процессах, порождённых через fork от одной уже загруженной машины, поэтому статические данные одного входа не протекают в следующий.

Обратной связи по покрытию здесь нет: входы не подстраиваются под то, до какого кода дошли предыдущие. Вход состоит из случайных байтов, порождённых из seed. Генератор, который знает формат, читает их как поток решений ([`input.rs`](https://github.com/irqlevel/nos/blob/master/fuzz/common/input.rs)). Чтение за концом входа всегда даёт ноль, а ноль всегда означает обычный выбор. И всё, что обрывает прогон раньше времени, должно случаться редко, иначе прогоны не уйдут вглубь:

```rust
/// True about once in 4096: for what ends a run, which has to be much
/// rarer than a run is long for the rest to be reached.
pub fn rare(&mut self) -> bool {
    self.u16() >= 0xFFF0
}
```

## Четыре фаззера

| Фаззер | Из чего собран | Целей | С чем сверяется |
|---|---|---|---|
| `fuzz/hv` | устройства гипервизора, local APIC и IO-APIC, декодер MMIO, обходчик таблиц страниц гостя, загрузчик Linux, таблицы ACPI, политика CPUID/MSR и цикл исполнения; коммутатор гостей, их DHCP-сервер и NAT | 22 | инварианты каждого устройства; модели коммутатора, NAT, политики и размещения гостей |
| `fuzz/net` | крейты `net`, `netwire`, `tls`, `fs` и `ssh` и исходник модуля sshd | 10 | модель внешнего мира, протокол за протоколом |
| `fuzz/fs` | крейты `block` и `fs` | 9 | модель дерева файлов, собственный e2fsck, отключения питания |
| `fuzz/cpp` | C++, который читает то, что ему дают прошивка, загрузчик или диск; загрузчик модулей; printf; таблицы страниц и куча | 11 | модель того, что обещает каждый заголовок, под ASan и UBSan |

Самая амбициозная цель hv, `platform`, собирает машину Linux-гостя так же, как это делает `hv boot`. Потом она запускает эту машину на настоящем цикле исполнения `LinuxGuest::run`, причём потоки vCPU работают строго по одному. Там, где цикл вошёл бы в гостя, сценарий решает, что гость сделает дальше. Гость может прочитать или записать порт ввода-вывода или MSR, обратиться к странице устройства (сценарий даёт и саму инструкцию обращения) или выполнить halt.

За много выходов из гостя (выходом называют момент, когда процессор покидает гостя и возвращает управление гипервизору) сценарий делает то же, что делают драйверы: от заполнения таблиц MSI-X до запуска остальных процессоров (AP) через INIT и SIPI. Находкой здесь считаются две вещи: vCPU, который входит в гостя с захваченной блокировкой, и цикл, который миллион раз читает часы, ни разу не войдя в гостя и не уснув.

`fuzz/net` окружает машину смоделированным миром ([`src/world`](https://github.com/irqlevel/nos/blob/master/fuzz/net/src/world/check.rs)). В нём есть канал, который задерживает, переставляет, дублирует и теряет пакеты, и TCP-пир, который хранит каждый байт обоих потоков. Есть rustls-сервер с собственным удостоверяющим центром фаззера, DHCP- и DNS-серверы, которые врут, и полноценный SSH-клиент.

`fuzz/fs` даёт слоям хранения диски с энергозависимым кэшем записи, выключателем питания и запросами, которые завершаются ошибкой ([`disk.rs`](https://github.com/irqlevel/nos/blob/master/fuzz/fs/src/machine/disk.rs)). Получившиеся образы он проверяет собственным e2fsck, который мы сверили с e2fsprogs на сотнях образов.

## Гейты и кампании

Без аргументов каждый фаззер прогоняет фиксированное число входов начиная с seed 1, и каждый раз это одни и те же входы. Поэтому его можно использовать как гейт, то есть проверку, которую должно пройти каждое изменение. CI запускает все четыре на каждый push: hv и fs в задании для x86-64, net и C++ в задании для arm64. Каждый работает от полуминуты до пары минут. Для кампании, долгого поиска новых ошибок, ту же программу запускают со своим seed:

```sh
python3 scripts/hv-fuzz.py                          # the gate
python3 scripts/hv-fuzz.py --seed 7 --seconds 300   # five minutes a target
python3 scripts/hv-fuzz.py --replay platform out/hv-fuzz/findings/X.hex
```

Каждая находка приходит вместе с seed и номером итерации, по которым её можно воспроизвести, а вход сохраняется для `--replay`. Фаззер завершается с кодом 0, если ничего не нашёл, 1 при находке и 3 при зависании. Насколько глубоко заходят входы, мы измеряем, а не угадываем. `HV_FUZZ_STATS=1` показывает, чем закончились прогоны всей машины. В первый же день гейт hv покрыл 94% регионов в компилируемых им исходниках, если считать по покрытию clang.

## Что они нашли

Каждый фаззер попал в репозиторий вместе с исправлениями того, что нашёл. Вот несколько находок.

### Гость, который мог выдать себя за другого

Цель `guestnet` соединяет коммутатор и NAT так же, как это делает модуль hv. На первом же входе она обнаружила, что гость может отправлять трафик от имени другого гостя. Коммутатор пропускал кадры с любым MAC и любым адресом. А NAT отправляет ответы потока на тот MAC, с которого пришёл последний пакет этого потока. Поэтому хватало одного пакета с адресом другого гостя и портами одного из его потоков, чтобы перехватить поток, и ответы внешнего мира уходили самозванцу.

Исправление ([d1aeecf](https://github.com/irqlevel/nos/commit/d1aeecf09004bba80ed5301eea6b25d60f1dc1d6)) делает то же, что виртуальный коммутатор в облаке. [`ingress`](https://github.com/irqlevel/nos/blob/master/src/rust/modules/hv/src/net.rs) проверяет каждый кадр гостя прямо на входе. Пропускаются только IPv4 и ARP, и только с MAC и адресом своего порта. Единственное исключение — DHCP-клиент, у которого адреса ещё нет, и ему коммутатор отвечает сам. Всё остальное отбрасывается и записывается на счёт гостя в `hv list`.

Однажды контрольный прогон с вырезанной проверкой показал, к чему это приводит: соединение через `hv forward` (эта команда пробрасывает порт nos в гостя) к веб-серверу одного гостя попало к другому. Теперь `hv-linux-test.py --net` заставляет настоящего Linux-гостя присвоить адрес соседа и проверяет, что обратно ничего не приходит.

### Адрес за верхней границей памяти

Гость мог положить буфер virtio на самый верх своего адресного пространства. Тогда виртуальный диск, записывая статус запроса, вычислял адрес за пределами 2^64. При `RUSTUB=1` это была паника, а в обычном ядре адрес молча заворачивался на страницу 0. Исправили это типом, а не проверкой в каждом месте вызова. Адрес сегмента теперь приватный, а единственный метод, который его выдаёт, складывает с проверкой переполнения ([`virtio.rs`](https://github.com/irqlevel/nos/blob/master/src/rust/hv/src/devices/virtio.rs)):

```rust
pub struct Seg {
    addr: u64,
    pub len: u32,
    pub write: bool,
}

impl Seg {
    pub fn at(&self, offset: u64) -> Option<u64> {
        if offset < u64::from(self.len) { self.addr.checked_add(offset) } else { None }
    }
}
```

В тот же первый день ([4ce4e77](https://github.com/irqlevel/nos/commit/4ce4e771b0f1f0d8cc2a662e0e10d1e913571b56)) нашлись ещё две ошибки. Остановленный командой halt vCPU крутился в цикле и занимал свой процессор на хосте: приоритеты гостя придерживали прерывание периодического APIC-таймера, а таймер сообщал дедлайн, который уже прошёл. А загрузчик Linux соглашался положить ядро по предпочтительному адресу ниже 1 МиБ, поверх нулевой страницы и таблиц страниц, которые он сам туда пишет. После исправлений кампании на десяти seed прогнали 7,9 миллиарда входов на финальной версии обвязки (кода фаззера вокруг исходников ядра) и больше ничего не нашли.

### Сон под спинлоком

Netconsole отправляет лог ядра по сети. Задача, которая выгружает в сеть его записи, опрашивает сетевое устройство, пока у того не появится адрес ([c68452d](https://github.com/irqlevel/nos/commit/c68452d5b7ab1ce09024cce09e050bcc4271090f)):

```diff
-            let nic = match self.log.lock().nic {
+            let attached = self.log.lock().nic;
+            let nic = match attached {
                 Some(nic) if nic.ip() != 0 => nic,
                 _ => {
                     kcore::task::sleep_ms(NO_LINK_POLL_MS);
                     continue;
```

Старая строка читается как «скопировать поле и отпустить блокировку», но делает она другое. Временное значение в выражении, которое проверяет `match`, живёт до конца всего `match`. Поэтому `IrqSpinLock` лога оставался захваченным все 200 мс сна, с выключенными прерываниями, а любой процессор, который в это время пытался записать строку трассировки, крутился на этой блокировке. Сон с захваченным спинлоком — именно то, что правила машины превращают в находку.

### Ошибки, которые выглядели как успех

Мир сетевого фаззера знает, что именно он отправил, и поэтому отличает обрезанный ответ от целого. Так нашлось целое семейство ошибок, в которых ядро сообщало об успехе. HTTP-ответ, оборванный посреди заголовков, возвращался с результатом «ok», а телом служила его же строка статуса.

TLS-клиент принимал за конец потока две вещи: поток, оборванный посреди записи, и истёкший таймаут приёма. Поэтому зависшее тело без указанной длины возвращалось как целое. DHCP-клиент после первого продления аренды начинал всё заново с DISCOVER, хотя аренда ещё действовала, и больше её не продлевал. Теперь он ведёт аренду так, как требует RFC 2131.

### Отключение питания между двумя записями

`create_file` в ext2 записывал новый inode раньше, чем бит в битовой карте, который помечает этот inode занятым ([07e7409](https://github.com/irqlevel/nos/commit/07e7409436ebde4f340b209d4f7a8b0288e2f5d3)):

```diff
-        if !self.write_inode(ino, &inode) || !self.flush_bitmap() || !self.commit_meta() {
+        if !self.flush_bitmap() || !self.write_inode(ino, &inode) || !self.commit_meta() {
```

Если питание пропадёт между этими двумя записями, inode окажется занят, а битовая карта будет считать его свободным, и его заберёт следующий create. Диск фаззера моделирует именно такое отключение.

Ещё две ошибки нашлись в других местах хранилища. Каталог, загрузка которого сорвалась на полпути, перечитывал свои записи при каждом обращении, так что каждый `ls` навсегда раздувал дерево. А disk log (он сохраняет лог ядра на диск для машин, которые умирают молча) на устройстве с 520-байтными секторами выходил за конец своего буфера на целую пачку. С `disklog=on` это была паника при загрузке.

### Индекс −1 при разборе дерева устройств

Загрузка arm64 первым делом читает дерево устройств, то есть описание оборудования от прошивки. В коде, который его разбирает, `END_NODE` без открытого узла уводил глубину обхода ниже корня. Тогда следующий узел записывал свои значения `#address-cells` и `#size-cells` по индексу −1 в стеки обходчика, а это запись в `.bss` ([00631ab](https://github.com/irqlevel/nos/commit/00631ab0b9cced3c6cb53c7ef623e04da0e24fa5)). Теперь свойства читаются через `Fdt::Prop`, и каждое чтение ограничено длиной свойства.

В том же раунде нашлись пулы кучи, которые выделяли страницу, не отпуская свой спинлок. Это тот самый дедлок из поста [о запрете аллокаций под спинлоком](/blog/no-allocation-under-spinlock).

### Не тот IO-APIC на AX41

Цель `acpi` ([516dc26](https://github.com/irqlevel/nos/commit/516dc2680ab97acaa11370cec0e722b8aa590d3e)) нашла две проблемы. Во-первых, каждая таблица из корневой таблицы ACPI навсегда оставалась отображённой в окне TmpMap. Это небольшой набор слотов, через которые ядро обращается к произвольным физическим страницам, и на AX41 таблицы занимали 21 из его 448 слотов. Во-вторых, если в таблицах было два IO-APIC, ядро оставляло последний.

MADT у AX41 перечисляет сначала IO-APIC южного моста FCH (GSI 0), а за ним IO-APIC северного моста GNB, так что ядро управляло вторым. Legacy-прерывания, включая тик HPET, настраивались на пинах, до которых не доходит ни одна из этих линий. Этого никто не замечал, потому что тик нужен только до тех пор, пока каждый процессор не запустит собственный local APIC-таймер. Ядро с исправлением, загруженное на AX41, показывает в `irqstat` тик с положенными 100 Гц.

Нашлась ошибка и в printf. `VsnPrintf` читал каждое целочисленное преобразование как 64-битный слот, поэтому `int`-уровень трассировки в каждом вызове `Trace` приходил вместе с тем, что лежало в старшей половине регистра ([3743fcf](https://github.com/irqlevel/nos/commit/3743fcf43965be6df80229dd859cd48db5080a8b)). Теперь форматы следуют правилам C, компилятор проверяет их через `PRINTF_FORMAT` и `-Wformat=2`, а цель `format` сверяет `VsnPrintf` с `vsnprintf` хоста байт в байт.

## Как убедиться, что обвязка ловит ошибки

Если фаззер ничего не находит, это может быть и хорошей новостью, и признаком обвязки, которая ничего не видит. Поэтому каждый фаззер мы проверили и с обратной стороны: ломаем код нарочно, и цель обязана упасть. Для трёх парсеров, от которых зависит загрузка x86, мы по одной убирали каждую проверку, всего 26, и каждая такая поломка становилась находкой в пределах 20 000 входов.

Сначала три поломки проскочили. В двух случаях генераторы не доходили до края: FADT (одна из таблиц ACPI), которая кончается ровно на границе поля, и карта памяти длиннее таблицы. В третьем случае эмулируемое окно TmpMap размечалось для ASan целыми страницами, поэтому чтение за концом короткой таблицы оставалось внутри доступной страницы. Чинили генераторы, а не ядро.

## Чего они не видят

Процессор в hv-фаззере — заглушка, поэтому из `hvarch` не фаззится ничего: ни его `unsafe`-код, ни VMCB и VMCS (структуры, в которых AMD-V и VT-x хранят состояние гостя), ни world switch между хостом и гостем. Порядок, в котором чередуются процессоры, тоже задаёт сценарий. Он проходит все пути между процессорами, но гонку так не найти.

`fuzz/cpp` не доходит до `PageTable::Setup`, которая работает на начальном линейном отображении, и до всего, что требует второго процессора. А в `fuzz/fs` записано одно известное ограничение: после ошибки устройства посреди create или rename каталог в памяти может расходиться с диском до следующего монтирования.

Фаззеры остаются гейтами, а целей становится больше: размещение гостей, политика CPUID и MSR (её сверяют с моделью, написанной по руководствам производителей, а не по коду) и файл микрокода Intel. Какой гейт что покрывает, написано на странице [о тестах и гейтах](/docs/testing), а как их запускать, рассказывает [отдельное руководство](/howto/run-the-gates).
