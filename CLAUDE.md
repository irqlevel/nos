# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It holds what every change has to know: the goal, the rules, how to build, and which gate to run. Reference material lives in `docs/` and is linked from where it is needed -- read the page before the work it covers.

`nos` is a hobby x86-64 / arm64 OS kernel written in C++20, Rust, and assembly. It is freestanding (no libc, no STL, no C++ exceptions/RTTI) and boots via Multiboot2/GRUB on x86-64 and the Linux `Image` protocol on arm64. It targets QEMU/KVM, KVM-based clouds (Google Cloud, Yandex Cloud), and QEMU `virt` + HVF on Apple Silicon, and boots on three real machines — a Dell Latitude 5480 (Skylake-U, UEFI, no serial port, no PS/2), where the framebuffer console and the xHCI USB keyboard are the only console channels, and two Hetzner dedicated servers, an Intel EX44 (RTL8125) and an AMD Ryzen AX41 (Intel I210), whose only console is the network. The long-term goal is a bare-metal cloud node running Linux guests under a Rust hypervisor (`plans/README.md`: stages 0–5, currently at the start of stage 3 -- `docs/hypervisor.md`).

## The goal: a kernel that is safe by design and by code

This is being built to be as safe as a kernel can be made: **no undefined behaviour, no memory corruption, no data races, no deadlocks, no resource leaks on error paths, no failure that passes in silence.** Not as a property to test for afterwards -- as the thing every design and every line is chosen for. It ranks above speed, above brevity and above getting a feature in sooner, and the long-term goal (other people's Linux guests on this machine) is why.

- **By design first.** Between two designs, take the one where the bug cannot be written over the one where a comment asks nobody to write it: a lock that owns what it guards, a handle that is looked up and not dereferenced, a ring lent under the lock that orders it, an image that is W^X. When something needs a rule to be used correctly, look for the type that makes the rule unnecessary -- the ones this tree has are listed in the Rust section.
- **By code.** The Conventions below are this, spelled out: Rust first and with as little `unsafe` as the job allows, C++ reviewed for undefined behaviour, every return value checked, every error path releasing what it took, nothing allocating or sleeping where a lock or an interrupt context forbids it.
- **A failure must be loud.** What cannot be ruled out is caught where it happens and reported, not left to surface as a wedge somewhere else: `BugOn` and `Panic` on a broken invariant, the TLB shootdown that names the CPUs that never answered instead of hanging the machine, the watchdogs, netconsole carrying a panic's backtrace off a box with no other console. A hang with no report is the worst outcome there is, and a change that turns one into a report is worth making.
- **A bug is a question about the design.** Fixing the instance is half of it; the other half is closing what made it possible, so that the next one of its kind does not compile, does not link, or fails a gate. The gates exist for the failures that look like success: write one when you meet another.
- **Neither speed nor safety is a guess.** A fast path may be structured differently to stay safe -- per-CPU state, a recycled pool, a lock-free ring -- but it does not drop a check or reach for `unsafe` on a hunch: measure, and say what was measured. "No behaviour change" is likewise something to show -- compare the binaries, run the gates -- not something to assert.

## Build, run, test

On macOS / Apple Silicon you almost always build inside Docker, which packages the whole toolchain (clang, nasm, grub-mkrescue, cppcheck, and the pinned nightly Rust):

```sh
./scripts/build-iso-docker.sh   # produces nos.iso + bin/kernel64.elf (GDB symbols)
./scripts/build-disk.sh         # produces nos.qcow2 (MBR disk image)
```

Native (Linux with the toolchain installed), or inside the container:

```sh
make            # = `make check` (cppcheck static analysis) + build nos.iso
make nocheck    # skip cppcheck, just build
make check      # run cppcheck only (fails the build on any finding, exit code 22)
make rust       # build only the Rust staticlib (src/rust → libkernel.a)
make smoke      # boot smoke test: build in Docker + headless QEMU, assert serial markers
make clean
make nocheck ARCH=aarch64   # arm64 -> kernel-arm64.elf + nos-arm64.img
make nocheck UBSAN=1        # the C++ under clang's UB sanitizer, either ARCH: the first report is a panic
make nocheck RUSTUB=1       # the Rust half under core's own checks of its unsafe preconditions, and overflow
```

The build is parameterized by `ARCH` (default `x86_64`; `aarch64` selects the arm64 toolchain, linker script and Rust target), and objects live in `out/$(ARCH)/`. What the Makefile will not tell you (`docs/build.md` has each at length):

- **Both architectures must stay green.** CI (`.github/workflows/ci.yml`) runs `make check` plus a build *and* a boot smoke test for `x86_64` and `aarch64`. A change to common code that only builds on x86 is a broken change.
- **Source lists are explicit, not globbed.** The Makefile has two hand-written lists, `CXX_SRC_x86_64` and `CXX_SRC_aarch64` (plus `ASM_SRC_*` for NASM and `ASM_S_SRC_*` for GNU-as). A new `.cpp` that is not added to the right list is silently not compiled; portable code must be added to **both**. Common driver code that references x86-only entry points gets an unreachable link stub in `src/cpp/arch/arm64/x86_driver_stubs.cpp` rather than an `#ifdef`.
- **Dependency files go stale.** After moving, renaming or deleting a header run a clean build, or delete the stale `.d` files in `out/`: they reference the old path, and make reports it as "No rule to make target".
- **The link is two-pass.** `out/$(ARCH)/pass1.elf` → `nm` → `out/$(ARCH)/symtab_data.cpp` (the table stack traces resolve symbols from) and the module export table → the final ELF. Remember it if you touch the link or symbol resolution (the `symtab_data` rules in the `Makefile`).
- **The Rust toolchain is a dated nightly and the external crates are vendored.** `src/rust/rust-toolchain.toml` pins it (the Dockerfile and both CI workflows install from there), `src/rust/vendor` holds the sources and the Makefile builds with `cargo --offline`, so no build touches the network. After changing a dependency -- or bumping the pin, which changes what std itself resolves to -- run `scripts/vendor.sh` and commit what it produces.
- **The kernel keeps SSE and the x87 off**, because it saves neither's state on a context switch. The x86 C++ is built with `-mno-sse -mno-80387` (arm64's with `-mgeneral-regs-only`), so floating point there compiles to calls to the soft-float helpers the Rust staticlib's `compiler_builtins` provides -- slow, and touching no FP register -- where `-mno-sse` alone let it fall back to x87 instructions without a word. A crate that dispatches to SSE2/AVX2 at run time cannot be built for such a target, or faults on the first AP that runs it: the RustCrypto crates are forced onto their software backends in `src/rust/.cargo/config.toml` (and `sha2` by its `force-soft` feature), and a new dependency of that kind needs the same. `getrandom` has no bare-metal backend either; `tls` registers the kernel entropy pool as its custom one (`docs/tls.md`).

### Gates

**Every refactor step must keep `./scripts/smoke-test.sh` green** (markers `After test` → `Preempt is now on` → `boot: complete`, fail-fast on `PANIC:`; `scripts/smoke-arm64.sh` is the arm64 equivalent, `SMOKE_HVF=1` for HVF; both take `--skip-build`). **Gate on exit codes, never on grepping output.** The x86 smoke boot attaches virtio-blk (modern), virtio-scsi (legacy), NVMe, virtio-net and virtio-rng, so it covers the Rust/MSI-X path too. CI boots a `UBSAN=1 RUSTUB=1` build on both architectures as well (docs/build.md): there, and under any gate run on one, the first undefined operation in the C++, and the first unsafe precondition `core` finds violated in the Rust, is a panic naming its site.

What a smoke boot cannot notice has a test of its own, each there for a failure that looks like success; when you meet another such failure, write another. Run the one that covers what you touched (`docs/testing.md` says what each does and why it exists):

### Running and debugging

```sh
./scripts/qemu.sh          # x86-64 ISO boot, 2 CPUs, virtio-net, GDB stub on :1234, serial -> nos.log
./scripts/qemu-disk.sh     # disk boot with virtio-blk/scsi/nvme/net/rng attached
./scripts/run.sh           # Linux/KVM, all host CPUs, isa-debug-exit device
./scripts/qemu-arm64.sh    # arm64 `virt`, the fast dev loop: HVF on Apple Silicon (~4x faster; NOS_TCG=1 forces TCG),
                           # virtio-mmio blk/net/rng, serial -> nos-arm64.log, UDP shell on :9000
python3 scripts/udpsh.py 127.0.0.1   # remote shell over UDP
./scripts/gdb64.sh         # GDB; QEMU must be started with -s (bin/kernel64.elf has the symbols)
./scripts/gdb-arm64.sh     # the same for arm64 (qemu-arm64.sh -s), needs gdb-multiarch
```

More in `docs/run.md` and `docs/debug.md`.

**Kernel command line**: set via GRUB (`build/grub.cfg`) on x86-64 or QEMU `-append` on arm64, parsed in `kernel/parameters.cpp`, listed in full in `docs/kernel-parameters.md`. To bisect a boot failure: `smp=off` (BSP only), `maxcpus=N` (the BSP included), `loglevel=N`, then take subsystems out of the path with `usb=off` (x86-64: skip xHCI bring-up), `its=off` (arm64: no ITS, MSI degrades gracefully), `hwrng=off`, `rc=off` (skip `/etc/rc`), `dhcp=auto|on|off`, `console=serial` / `console=vga`. On a machine with no serial port `netconsole=ip:port` is the only way to see the log of a boot that dies -- `scripts/netconsole.py` receives it, `nctail=N` keeps the newest N KiB of the pre-link backlog -- and `disklog=on` is for a boot that dies before its network is up.

**Tests run at boot, not via a test runner.** Self-tests live in `src/cpp/kernel/test.cpp`, each a `Stdlib::Error TestXxx()` run from `Test::Test()` (called in `main.cpp:Main2`) or `Test::TestMultiTasking()`; `rust_test` runs the Rust side's from the same place. To add one, write a `TestXxx()` and register it in the `Test()` dispatcher. **To run a single test, edit `Test()` to call only that function**, rebuild, boot, and watch `nos.log`.

## Architecture

Boot flow (x86-64), in full in `docs/boot.md`: `arch/x86_64/boot64.asm` (Multiboot2 entry, 32→64-bit transition, AP trampoline) → `kernel/main.cpp` `Main2` (BSP: paging, dmesg, page allocator, runs `Test()`) → `BpStartup` (interrupts, IOAPIC, timers, brings up APs via INIT/SIPI, starts SoftIrq/TCP/shell, prints `boot: complete`). APs enter via `ApMain` → `ApStartup`. On arm64 the equivalent path is `arch/arm64/boot.S` → `arch/arm64/main_arm64.cpp`, with PSCI `CPU_ON` for APs.

Source layout (directory by directory in `docs/project-layout.md`):

- **`src/cpp/` is the fundamentals.** `hal/` — the portable contracts, each header selecting the arch backend at compile time; `arch/x86_64/` and `arch/arm64/` — everything arch-specific, from the boot entry to the PTE encoding; `kernel/` — the scheduler, tasks, interrupt dispatch, SoftIrq, timers, locks, panic and backtrace, dmesg, the shell (`cmd.cpp`), the random pool, the self-tests (`test.cpp`), the module loader (`module.cpp`) and the Rust bridge (`rust_ffi.cpp`); `mm/` — page tables, the page, pool and VA allocators, `new`/`delete`; `drivers/` — serial, the console, PIT/HPET/RTC, the 8042 keyboard, PCI, MSI-X, ACPI, and **no virtio and no USB**; `lib/` — `Stdlib::`, the freestanding stdlib and containers.
- **`src/rust/` is everything on top**, a cargo workspace built into a `#![no_std]` `staticlib` (`libkernel.a`): `ffi/` (raw `extern "C"` declarations only) and `kcore/` (safe RAII wrappers around kernel services); **the whole block layer** (`block/`), **the whole network layer** (`net/`, over the frame formats in `netwire/`) and **the whole filesystem layer** (`fs/`: the VFS over ext2 read-write, nanofs, ramfs and procfs) -- there is no `src/cpp/{block,net,fs}` and no C++ view of any of them; `virtio/` and `drivers/` (`virtio_blk`, `virtio_net`, `virtio_scsi`, `virtio_rng`, `nvme`, `usb`, `r8168`, `r8125`, `igb`); `tls/` (rustls) and `ssh/` (the protocol, with no kernel in it) -- with `sha2` in `kernel/`, the only external dependencies in the tree, all vendored; `hvarch/` + `hv/` (the hypervisor: the CPU's virtualization extension and all of its `unsafe`, and the safe half above it -- workspace members but **not** default members, so they are compiled only into the `hv` module and a kernel without it carries no hypervisor at all); `kernel/` (entry points, the global allocator); `kmod/` + `modules/` — **loadable modules**, Rust-only, each built on its own into a `.ko` that `insmod` binds against an export table generated from the `ffi` declarations.
- **Dependencies run one way**: a driver depends on `block` or `net`, `fs` on `block`, `net` on `fs` and `tls` -- which is below `net`, so it takes its transport as a trait.

## Conventions (critical)

This file is the authoritative copy of the project's rules: `docs/` explains and expands them, and where the two disagree this file wins. They are how the goal at the top is kept in practice. First which language new code is in, then the non-obvious rules -- C++ first, and then what goes for both:

- **New code is Rust unless it has to be C++.** C++ is for the fundamentals that are C++ already, and for extending those in place: boot and arch bring-up, the MMU and the allocators, the scheduler and tasks, the locks, interrupt dispatch, timers, the HAL, the core of the shell, the module loader. Everything that sits on them is Rust: every driver (block, net, USB, virtio, anything on the PCI bus), every network protocol and service, every filesystem, the block layer, and the shell commands that belong to any of those -- a new command goes in the crate that owns the data (`igbdump` is in `drivers/igb`), not in `cmd.cpp`. Do not add a C++ view of a Rust layer or grow a C ABI so that new C++ can reach Rust: if new C++ would need one, the code is on the wrong side. When a C++ subsystem has to be reworked substantially anyway, moving it to Rust is the preferred direction. **What is optional is a loadable module** (`src/rust/modules/`, `docs/modules.md`): a server, a load generator, a diagnostic -- anything a machine can boot and run without -- is a `.ko` over `kcore`, as `sshd`, `netblk`, `netload` and `blkload` are. The one thing a module cannot be today is a disk's or a NIC's driver: those register with their layer as trait objects from inside the image, and there is no C name for a module to bind.
- **Freestanding constraints**: no `std::` (use `Stdlib::` from `lib/stdlib.h`), no exceptions/RTTI, **no lambdas/closures**, no `thread_local`, no heap before `PageAllocatorImpl::Setup()`. `volatile` compound assignments are banned — write `x = x + y`.
- **Static constructors do not run, and the link refuses one.** This kernel runs no `.init_array`, so a global whose type has a non-`constexpr` constructor or a non-trivial destructor would be left as zeroes -- `Pci`'s config lock and the arm64 console's sat unregistered with the watchdog that way for as long as they existed -- and both linker scripts now fail such a build ("a static constructor or destructor"). Give the type a `constexpr` constructor and a trivial destructor, every member initialised (as `Atomic` and `RawRwSpinLock` have), or make the object a function-local static: the singleton + explicit init pattern, `static Foo& GetInstance(){ static Foo i; return i; }` plus a `bool Setup()` called once at boot. Heap-allocate non-trivial objects (e.g. `Mm::TAlloc<T, Tag>()`) rather than using static arrays of them.
- **Error handling**: return `bool`/pointer for pass-fail, `Stdlib::Error` (`lib/error.h`, carries code, file, line and function) for rich errors, `Stdlib::Result<T>` (`lib/result.h`) for value+error. Build with `MakeError(Stdlib::Error::NoMemory)` / `MakeSuccess()`; a `Result<T>` converts implicitly from a `T` and from an `Error`, so `return 42;` and `return MakeError(...);` are both all it takes. Always check return values. On error paths, release every resource acquired so far in reverse order. `BugOn(cond)` and `Panic("fmt", …)` for invariant violations.
- **OOM and `operator new`**: plain `new T(...)` **panics on OOM** and never returns `nullptr` — the compiler assumes the plain form is non-null, so a null check after it is dead code. Fallible allocations must use `new (Mm::NoThrow) T(...)` (the compiler keeps that null check; from `Stdlib::` code it is spelled `new (Kernel::Mm::NoThrow) T[...]`, as in `lib/vector.h`) or `Mm::TAlloc<T, Tag>()`, and check the result. Why the plain form cannot be made nullable is in `mm/new.h` and `docs/paging.md`.
- **Never allocate or free with a spinlock held.** `Mm::Free`/`Mm::Alloc` reach the page allocator, which shoots down the TLB on every other CPU (`CpuTable::InvalidateTlbRange` → IPI → `WaitGroup::Wait`) and waits for all of them to answer. A CPU spinning on the lock you hold has interrupts off and can never answer, so the two wait for each other forever -- no panic, nothing to reset the machine. Collect what needs releasing into a local list under the lock, unlock, then release. Better still, do not allocate on a datapath at all: net frames come from the frame pool, built once at boot and recycled through per-CPU caches over a lockless ring, and a driver hands a finished TX frame to `TxQueue::done` -- the only way out of `flush_tx` a frame has -- for the net layer to release off the lock. `CpuTable::SendTlbIPI` panics after ten seconds naming the CPUs that never answered, so a new instance of this bug is a report rather than a dead machine.
- **Memory refcounting** is explicit and easy to get wrong — `PageTable::MapPage(va, page)` does `+1`, `GetPage(phyAddr)` does `+1` (caller must `Put()`), `UnmapPage(va)` is net-0 (a `Get` and a `Put` inside) and returns the `Page*`. To fully undo a `MapPage`: `UnmapPage`, then `page->Put()`. To free a mapped page: `UnmapPage` + `FreePage` + `Put`. `FreePage` alone only puts the page back on the free list; it does not touch the refcount (the table is in `docs/paging.md`).
- **Never map DMA/device memory at `physAddr + KernelSpaceBase` directly.** Always go through `Mm::MapPages` / `Mm::AllocMapPages` so the `VaAllocator` tracks the VA. `Mm::AllocMapPages` / `UnmapFreePages` allocate contiguous frames and free them on release; `Mm::MapPages` / `UnmapPages` map frames the caller supplies and keeps (`mm/new.h`; the table is in `docs/paging.md`).
- **The kernel image is W^X on both arches.** Late in boot `ProtectRange` splits it into text RX / rodata RO+NX / data RW+NX (`main.cpp`, `main_arm64.cpp`), and MMIO mappings are NX. Self-modifying code, executing from a heap buffer, or writing through a pointer into `.rodata` faults instead of silently working.
- **Memory barriers**: `Barrier()` is gone. Pick the semantic variant from `hal/barrier.h`: `Hal::SmpWmb/SmpRmb` (CPU↔CPU publish/consume, e.g. seqlock), `Hal::DmaWmb/DmaRmb` (CPU↔device rings/doorbells/OWN bits), `Hal::CompilerBarrier` (compiler-only). On x86 they all compile to a compiler barrier; on arm64 they become `dmb` — misclassification is invisible on x86 and bites on arm64. In Rust, device ordering uses `kcore::barrier::dma_wmb/dma_rmb` (`dmb oshst/oshld` on arm64) — `core::sync::atomic::fence` is NOT a substitute: it emits `dmb ish`, whose inner-shareable domain does not order against a PCIe master. Consuming device-written state needs a read barrier *after* the index/phase/OWN check and before the payload reads (an address-independent load pair is not ordered by a control dependency on arm64) — see `virtio::Queue::take_used`, nvme `read_cqe`, r8168 `harvest`.
- **Write Rust with as little `unsafe` as the job allows, and put what is left in `kcore` and at the C ABI, not in the layers.** A new driver, protocol, filesystem or module should need none of its own beyond an `unsafe impl` saying a struct is plain words and the entry point C++ calls it by. Reach for the `kcore` type first (the list is in the next section, the long form in `docs/rust.md`); when the shape you need has none, add the type to `kcore` -- once, with the reason it is sound in its comment -- rather than an `unsafe` block at every use. Do not lower the count by hiding it: a pointer kept as a `usize`, a macro that folds ten blocks into one, a safe wrapper that trusts what it is given, all leave the risk and remove the warning. `scripts/unsafe-count.py [crate...]` counts the sites (blocks, `unsafe fn`, `unsafe impl`); a change that raises a layer's or a driver's number should be able to say why.
- **Arch discipline**: common code includes `hal/*` headers only; an architecture's own headers are for arch code, x86-only drivers and three documented exemptions (`kernel/main.cpp`, `kernel/cmd.cpp`, `kernel/irq_balance.cpp`). `Hal::` wrappers: `IsInterruptEnabled`, `IrqSave/IrqRestore` (not RFLAGS), `GetSp/SetSp/GetFp` (not GetRsp/GetRbp), `ReadCycleCounter` (not ReadTsc), `IrqEoi/SendIpi/GetCurrentCpuHwId` (not Lapic::), `TlbFlushPage/TlbFlushAll` (not Invlpg/CR3). Per-arch member functions (e.g. `CpuTable::StartAll`) live in arch TUs.
- **Style**: namespaces `Kernel::`, `Kernel::Mm::`, `Stdlib::`. Trace with `Trace(level, "fmt", …)` / Rust `trace!(...)`; level 0 is always visible and the per-subsystem level constants (`KbdLL`, `UsbLL`, `PageAllocatorLL`, …) are at the top of `kernel/trace.h`. To debug a subsystem raise one there, or raise the global level with the `loglevel N` shell command or the `loglevel=N` boot parameter -- no rebuild, which is what you want on a box whose only console is a UDP socket. No magic numbers: name constants (`static const`, `constexpr` or an `enum`, in the header or class they belong to). `/* ... */` for a multi-line comment, `//` for a one-line one; `auto` is fine for a deduced local, and the smart pointers in `lib/` are there to be used. Preserve existing formatting; don't reflow unchanged code. 4-space indent.
- **C++ gets a second pass for undefined behaviour before it is done.** Once it is written and builds, re-read the diff looking for nothing else: `-Wall -Wextra -Werror` and cppcheck catch little of it, and in a kernel UB is not a crash at the faulty line but a machine that wedges somewhere else, on one architecture, at one optimisation level. What to look for, most of it from bugs this tree has had: a value from outside -- a device register, a packet, a disk, the Rust side, the shell -- used as an index, a length, a shift count or a handle before it is range-checked (`1 << n` with `n` from hardware, `count * size` that can wrap, a PCI slot shifted into an address unmasked); signed overflow and conversions that truncate; a read of anything not yet initialised, padding copied out and members a constructor skips included; a `reinterpret_cast` onto bytes that may be misaligned or are another type's (wire and on-disk structures go through `MemCpy` or byte accessors); a pointer or reference that outlives what it points at -- a stack object handed to a callback, a list entry freed while still linked, an object freed while an interrupt handler or another CPU may still hold it; shared state touched from two CPUs or from an interrupt without the lock, the atomic or the barrier that orders it, and `volatile` standing in for any of those; a null check after plain `new`, or none after a fallible allocation; a static object with a constructor; control falling off the end of a non-void function. Say in the change what was checked and what was found. Then run the gate for the code on a `UBSAN=1` build (docs/build.md): it catches at run time what the read missed on the paths the gate drives -- and nothing on the paths it does not, so it does not replace the read.
- The C++ build uses `-Wall -Wextra -Werror`, so warnings break the build.

## Rust: `ffi`, `kcore`, the layers, the drivers

`docs/rust.md` is the long form of this section -- the reason behind each rule, a map of what `kcore` has, how a driver is written -- and `docs/modules.md` is the same for a module. Read it before writing Rust here. What must not be missed:

- **A kernel service reaches Rust in three steps**: the C++ function in `src/cpp/kernel/rust_ffi.cpp` (all of the bridge's C++ lives in that one file), its raw declaration in `src/rust/ffi/src/<module>.rs`, the safe wrapper in `src/rust/kcore/src/<module>.rs`. A module gets it by the same three: its export table is generated from the `ffi` declarations, and a change to them changes the digest every `.ko` carries, so modules are rebuilt with the kernel.
- **`ffi/` is declarations only**: raw pointers, no references, a kernel object an opaque `usize` handle, 0 for failure. The blocks are `unsafe extern "C" {` **at the start of a line** -- the Makefile's export table looks for exactly that. `pub safe fn` is for a function that is sound for *any* argument at *any* time, and only after reading its definition: values-only C++ that validates them, or a Rust export that only looks its handle up in a table. Not for anything with a buffer, a callback or a C++ handle; not for the PCI config reads (the arm64 ECAM accessor does not bound the slot or the function); not for `irq_restore` or `preempt_enable`, which can open a window inside somebody else's critical section.
- **`kcore/` is where a handle becomes a type**: `Drop` calls the matching `kernel_*_destroy` / `kernel_*_stop` / `kernel_*_put`, a handle that must not be `Send`/`Sync` carries `PhantomData<*const ()>`, and ownership crosses to C++ inside the wrapper, so no call site has a `forget` to remember. Its `block`, `net`, `tcp` and `fs` modules are those layers *as a loadable module reaches them*; inside the image the crates call each other as crates (`block::Disk`, `net::Nic`, `net::Frame`, `fs::vfs::Open`).
- **The C ABI is for what is on the other side of a link** -- C++, or a module. Between two pieces of Rust in the image the seam is a trait or a `&mut dyn` (`vfs::FileSystem`, `http::Sink`, `UdpHandler`, `tls::Transport`, `BlockDriver`, `NetDriver`), not an `extern "C" fn(ctx: *mut u8, …)` table. An export that trusts a pointer is `unsafe extern "C" fn` with a `# Safety` section, and **an export nobody calls is deleted**, not kept for symmetry. A C++ file that needs a Rust layer declares the `rust_*` / `kernel_*` calls it makes where it makes them. What a layer and a module both need, and that needs no kernel, is a crate with no kernel in it (`netwire`, `ssh`): a module is linked on its own and cannot link a layer, so anything else would be written twice. **A small function on a datapath that another crate calls is `#[inline]`** -- there is no LTO, so without it an accessor is a call with bounds checks of its own, in the image and twice over in a module (`docs/rust.md` has the numbers).
- **Before an `unsafe` block, look for the type that makes it unnecessary** (the reason each is sound is in the type's own comment):
  - data under a lock: `Mutex<T>`, `SpinLock<T>`, `IrqSpinLock<T>`, `PreemptSpinLock<T>`, `TryLock<T>` -- a lock owns what it guards, never a bare lock beside an `UnsafeCell`
  - the one of something: a `Once`/`OnceBox` static; per-CPU state: `PerCpu<LocalCounter…>` or `CpuLocal<T>`, never an array indexed by `cpu::id()`
  - what only the receive path touches: an `RxOwned<T>`, reached with the `&mut RxContext` a `UdpHandler` is lent
  - an on-disk or on-wire structure: `kcore::pod`
  - a handle from outside -- a net device, a TCP connection, a block device, an open file: **looked up in its table, not dereferenced**, so a bad one is `None` rather than undefined behaviour
  - a graph: an arena and ids (`fs::vnode::Tree`), not raw pointers
  - a callback -- interrupt, timer, soft IRQ, task: a function item over its `&'static` target (`MsixInterrupt::register_for(&table, 0, dev, Dev::interrupt)`), with no `ctx` to cast and no closure that captures
  - device memory: a descriptor ring is a `&'static [D]` of `Volatile` cells (`DmaBuffer::leak_ring`), and anything else in a `DmaBuffer` crosses through `load`/`store`/`bytes`
  - what waits when dropped -- a `UdpListener`, a `TaskHandle`, an interrupt handle: in its own `Lock<Option<..>>`: `take()` it under the lock, drop it after. Dropped under the lock its wait needs, it is a deadlock
- **A driver** implements `block::BlockDriver`, `net::NetDriver` or `kcore::entropy::Source` over a device that is `Box::leak`ed and so `&'static`; shutdown is `quiesce(&self)`, not a `Drop`, and nothing is freed. An interrupt handler runs in IRQ context and may run on two CPUs at once: registers, atomics and IRQ-safe locks, no sleeping, no allocating. A NIC's rings are its `NetDriver::Tx`/`Rx`: `net::register` takes them over -- last, because from there on the driver is called -- and lends them as `&mut` to `flush_tx` and `process_rx`, so nothing else can reach them; a finished TX frame goes to `TxQueue::done`, never dropped there (the spinlock rule). The smallest real example of each kind: `drivers/virtio_blk` (`drivers/nvme` for the asynchronous path), `drivers/r8168`, `drivers/virtio_rng`.
