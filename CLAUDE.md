# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`nos` is a hobby x86-64 / arm64 OS kernel written in C++20, Rust, and assembly. It is freestanding (no libc, no STL, no C++ exceptions/RTTI) and boots via Multiboot2/GRUB on x86-64 and the Linux `Image` protocol on arm64. It targets QEMU/KVM, KVM-based clouds (Google Cloud, Yandex Cloud), and QEMU `virt` + HVF on Apple Silicon, and boots on three real machines — a Dell Latitude 5480 (Skylake-U, UEFI, no serial port, no PS/2), where the framebuffer console and the xHCI USB keyboard are the only console channels, and two Hetzner dedicated servers, an Intel EX44 (RTL8125) and an AMD Ryzen AX41 (Intel I210), whose only console is the network (see `docs/real-hardware.md`). See `docs/features.md` for the full feature list, `docs/shell-commands.md` for the shell command reference (index in `docs/README.md`), `docs/boot.md` / `docs/paging.md` / `docs/scheduler.md` / `docs/interrupts.md` / `docs/profiler.md` / `docs/random.md` for how those subsystems work, and `plans/README.md` for the roadmap (the long-term goal is a bare-metal cloud node running Linux guests under a Rust hypervisor — stages 0–5, currently at the end of stage 2).

## The goal: a kernel that is safe by design and by code

This is being built to be as safe as a kernel can be made: **no undefined behaviour, no memory corruption, no data races, no deadlocks, no resource leaks on error paths, no failure that passes in silence.** Not as a property to test for afterwards -- as the thing every design and every line is chosen for. It ranks above speed, above brevity and above getting a feature in sooner, and the long-term goal (other people's Linux guests on this machine) is why.

- **By design first.** Between two designs, take the one where the bug cannot be written over the one where a comment asks nobody to write it: a lock that owns what it guards, a handle that is looked up and not dereferenced, a ring lent under the lock that orders it, an image that is W^X. When something needs a rule to be used correctly, look for the type that makes the rule unnecessary -- the ones this tree has are listed in the Rust section.
- **By code.** The Conventions below are this, spelled out: Rust first and with as little `unsafe` as the job allows, C++ reviewed for undefined behaviour, every return value checked, every error path releasing what it took, nothing allocating or sleeping where a lock or an interrupt context forbids it.
- **A failure must be loud.** What cannot be ruled out is caught where it happens and reported, not left to surface as a wedge somewhere else: `BugOn` and `Panic` on a broken invariant, the TLB shootdown that names the CPUs that never answered instead of hanging the machine, the watchdogs, netconsole carrying a panic's backtrace off a box with no other console. A hang with no report is the worst outcome there is, and a change that turns one into a report is worth making.
- **A bug is a question about the design.** Fixing the instance is half of it; the other half is closing what made it possible, so that the next one of its kind does not compile, does not link, or fails a gate. The gates exist for the failures that look like success: write one when you meet another.
- **Neither speed nor safety is a guess.** A fast path may be structured differently to stay safe -- per-CPU state, a recycled pool, a lock-free ring -- but it does not drop a check or reach for `unsafe` on a hunch: measure, and say what was measured. "No behaviour change" is likewise something to show -- compare the binaries, run the gates -- not something to assert.

## Build, run, test

The kernel needs an x86-64 cross toolchain: clang, nasm, ld, grub-mkrescue + `xorriso`/`mtools`, cppcheck, and a **nightly** rustup toolchain with `rust-src` (the staticlib needs `-Z build-std` and `#![feature(alloc_error_handler)]`). The nightly is pinned to a *dated* channel by `src/rust/rust-toolchain.toml`, which the Dockerfile and both CI workflows install from, because the vendored dependency sources only resolve against that one. On macOS / Apple Silicon you almost always build inside Docker, which packages the whole toolchain:

```sh
./scripts/build-iso-docker.sh   # produces nos.iso + bin/kernel64.elf (GDB symbols)
./scripts/build-disk.sh         # produces nos.qcow2 (MBR disk, needs --privileged Docker)
```

Native build (Linux with the toolchain installed):

```sh
make            # = `make check` (cppcheck static analysis) + build nos.iso
make nocheck    # skip cppcheck, just build
make check      # run cppcheck only (fails the build on any finding, exit code 22)
make rust       # build only the Rust staticlib (src/rust → libkernel.a)
make smoke      # boot smoke test: build in Docker + headless QEMU, assert serial markers
make clean
```

The build is parameterized by `ARCH` (default `x86_64`; `aarch64` selects the arm64 toolchain, linker script and Rust target). Objects live in `out/$(ARCH)/`. After moving, renaming or deleting a header run a clean build, or delete the stale `.d` files in `out/`: they reference the old path, and make reports it as "No rule to make target".

**Both architectures must stay green.** CI (`.github/workflows/ci.yml`) runs `make check` plus a build *and* a boot smoke test for `x86_64` and `aarch64`. A change to common code that only builds on x86 is a broken change.

**Source lists are explicit, not globbed.** The Makefile has two hand-written lists, `CXX_SRC_x86_64` and `CXX_SRC_aarch64` (plus `ASM_SRC_*` for NASM and `ASM_S_SRC_*` for GNU-as). A new `.cpp` that is not added to the right list is silently not compiled; portable code must be added to **both**. Common driver code that references x86-only entry points gets an unreachable link stub in `src/cpp/arch/arm64/x86_driver_stubs.cpp` rather than an `#ifdef`.

### Gates

**Every refactor step must keep `./scripts/smoke-test.sh` green** (markers `After test` → `Preempt is now on` → `boot: complete`, fail-fast on `PANIC:`; `scripts/smoke-arm64.sh` is the arm64 equivalent, `SMOKE_HVF=1` for HVF). Gate on exit codes, never on grepping output. The x86 smoke boot attaches virtio-blk (modern), virtio-scsi (legacy), NVMe, virtio-net and virtio-rng, so it covers the Rust/MSI-X path too. What a smoke boot cannot notice has a test of its own, each one there for a failure that looks like success:

| Gate (`scripts/`) | Arch | What it checks | Run it after touching |
|---|---|---|---|
| `wx-test.sh [--arch x86_64\|aarch64]` | both | boots once per probe (`wxprobe=text`, `wxprobe=heap`) and fails if the kernel survives one | a mapping path: no smoke boot notices a mapping that stops being NX |
| `parttest.py [--arch aarch64\|x86_64]` | both | an MBR disk and a GPT disk it writes itself, and what the kernel made of them | the block layer: the smoke disks carry no partition table at all |
| `ext2-test.py` | arm64 | works the root filesystem from the shell, then lets `e2fsck` judge the image | ext2: a smoke boot checks that the driver reads back what it wrote, not that the disk is still consistent |
| `nanofs-test.py` | arm64 | format, the `fstest` self-test, files read back from a second mount, then the image parsed by the script itself | nanofs, which no smoke boot touches: a driver reading back its own writes never notices a field at the wrong offset |
| `disklog-test.py` | arm64 | boots with `disklog=on` over an area it prepares, reads it back with `scripts/disklog.py`: the first fifty traced lines against the serial console's | the disk log: nothing else gives `disklog=on`, and without it no disk is so much as read |
| `netconsole-test.py` | arm64 | the log streamed to a collector it runs: the pre-link backlog, no gaps in the sequence numbers, lines after link-up, a panic's report with its backtrace | the trace path, the net device, netconsole: on the Hetzner boxes it is the only console there is |
| `tcp-test.py` | arm64 | fetches from an HTTP server it runs: a 400 KB body by SHA-256, a refused connection, one that has to time out, twelve in a row through TIME-WAIT, the connection table back where it started | TCP, HTTP: a slot leaked per connection is invisible until the sixty-fourth |
| `sshd-test.py` | arm64 | the listening side of TCP, the module loader and the sshd module. 40 checks pass; `poweroff unloads sshd before the unmount` fails for reasons of its own | TCP accept, modules, the ffi declarations (a module's ABI digest hashes them) |
| `netblk-test.py [--arch x86_64\|aarch64]` | both | the netblk module serving an NVMe disk, and a partition of a second one, over UDP, worked from outside with `scripts/netblk.py`: geometry, data written and read back, requests it has to refuse, a load test each way, a stop and an `rmmod` that leave nothing behind | the block layer's asynchronous path, and the C ABI a module reaches `block` and `net` through |
| `netload-test.py` | arm64 | every `netload` echo byte for byte, a burst longer than the reply batch, sink mode, more start/stop rounds than a device has listener slots, the frame pool back where it began | the receive path, the frame pool: nothing else answers from inside the receive path, or notices a pool that was never built -- which is how a boot that passed every other gate spent two hours taking each frame from the allocator |
| `usb-test.py` | x86-64 | an emulated xHCI controller, a keyboard on a root port and one behind a hub, a device that is neither; it **types at the kernel through QEMU's monitor** and reads the shell's answer off the serial console | `drivers/usb/`: no smoke boot attaches a USB controller, and a driver that enumerates perfectly and delivers no report passes every boot-log check |

`tcp-test.py` and `netload-test.py` take `--nic igb`, which swaps virtio-net for QEMU's 82576 (QEMU 8.0 or later; CI's does not have it, so this one is run by hand). It is the only way any of the three hardware NIC drivers runs anywhere but on a Hetzner box -- MSI-X with two vectors, the descriptor rings, the receive poll and its interrupt throttle -- so run both after touching `drivers/igb` or the driver seam in `net/src/device.rs`. `r8168` and `r8125` have no emulation at all: a change to either is checked by the compiler and then on the EX44, whose only console is that NIC, so keep their register sequences as they are.

### Running and debugging

Run in QEMU (serial console is logged to `nos.log`):

```sh
./scripts/qemu.sh        # ISO boot, 2 CPUs, virtio-net, GDB stub on :1234
./scripts/qemu-disk.sh   # disk boot with virtio-blk/scsi/nvme/net/rng attached
./scripts/run.sh         # Linux/KVM, all host CPUs, isa-debug-exit device
```

arm64 (QEMU `virt`, HVF-accelerated on Apple Silicon — the fast dev loop):

```sh
make nocheck ARCH=aarch64      # (in Docker on macOS) -> kernel-arm64.elf + nos-arm64.img
./scripts/qemu-arm64.sh        # boots nos-arm64.img with virtio-mmio blk/net/rng,
                               # serial -> nos-arm64.log, UDP shell on :9000
                               # (NOS_TCG=1 forces TCG; HVF is ~4x faster)
python3 scripts/udpsh.py 127.0.0.1   # remote shell over UDP
./scripts/gdb-arm64.sh         # attach GDB (qemu-arm64.sh -s), needs gdb-multiarch
```

PCIe on arm64 (ECAM + GICv3 ITS) works end-to-end: NVMe-over-MSI delivers interrupt-driven completions via ITS LPIs. `its=on` is the default; boot with `its=off` to disable the ITS and degrade MSI gracefully (virtio-mmio devices don't need it).

Debug with GDB (QEMU must be started with `-s`):

```sh
gdb -ex "symbol-file bin/kernel64.elf" -ex "set architecture i386:x86-64" -ex "target remote :1234"
# or: ./scripts/gdb64.sh
```

### Kernel command line

Set via GRUB (`build/grub.cfg`) on x86-64, or QEMU `-append` on arm64; parsing lives in `kernel/parameters.cpp`. Useful when bisecting a boot failure: `smp=off` (BSP only), `maxcpus=N` (start at most N CPUs, the BSP included), `console=serial` / `console=vga`, `dhcp=auto|on|off`, `dns=on`, `udpshell=PORT`, `usb=off` (x86-64: skip xHCI bring-up), `its=off` (arm64), `hwrng=off` (ignore RDRAND/RDSEED/RNDR, so the entropy pool falls back on virtio-rng and timing jitter -- see `docs/random.md`), `rc=off` (skip `/etc/rc`, the shell commands the shell's task runs once the network is up -- see `docs/sshd.md`), `loglevel=N`.

`netconsole=ip:port` streams the whole kernel log to that UDP collector as each line is produced (buffered until the network is up, panic report included) -- receive it with `scripts/netconsole.py`; on a machine with no serial port this is the only way to see the log of a boot that dies. Each datagram carries a sequence number so the collector can report gaps, and the drain is paced at one datagram per millisecond: an unpaced backlog burst is dropped by the first narrow queue on the way out, which looks exactly like a hang. `nctail=N` caps the pre-link backlog at the newest N KiB, so a machine that wedges just after the network comes up sends the lines around the wedge rather than the head of the boot log.

### Tests run at boot, not via a test runner

There is no separate test binary. Self-tests live in `src/cpp/kernel/test.cpp`; each is a `Stdlib::Error TestXxx()` function, run from `Test::Test()` (called in `main.cpp:Main2`) and `Test::TestMultiTasking()`, early during boot; `rust_test` runs the Rust side's from the same place. To add a test, write a `TestXxx()` and register it in the `Test()` dispatcher. **To run a single test, edit `Test()` to call only that function**, rebuild, and boot — watch `nos.log`. A failing test returns a non-success `Stdlib::Error`.

### Symbol table is generated by a two-pass link

Stack traces resolve symbols from a table baked into the kernel. The build links `out/$(ARCH)/pass1.elf`, runs `nm` over it to generate `out/$(ARCH)/symtab_data.cpp`, then links the final kernel ELF (the module export table is made from pass 1 the same way). If you touch the link or symbol resolution, remember this two-pass flow (see the `symtab_data` rules in the `Makefile`).

## Architecture

Boot flow (x86-64), in full in `docs/boot.md`: `arch/x86_64/boot64.asm` (Multiboot2 entry, 32→64-bit transition, AP trampoline) → `kernel/main.cpp` `Main2` (BSP: paging, dmesg, page allocator, runs `Test()`) → `BpStartup` (interrupts, IOAPIC, timers, brings up APs via INIT/SIPI, starts SoftIrq/TCP/shell, prints `boot: complete`). APs enter via `ApMain` → `ApStartup`. On arm64 the equivalent path is `arch/arm64/boot.S` → `arch/arm64/main_arm64.cpp`, with PSCI `CPU_ON` for APs.

Source layout (detailed in `docs/project-layout.md`):

- `src/cpp/hal/` — portable HAL contracts (cpu/atomics, semantic barriers, mmu+pte, irqchip, console, pci, power, Context, IRQ stub symbols, the cpu's random instruction); each header selects the arch backend at compile time
- `src/cpp/arch/x86_64/` — everything x86-specific: Multiboot2 entry + AP trampoline (`boot64.asm`), CPU primitives (`asm.asm`, `asm.h`), IDT/GDT, exceptions, TSC/kvmclock, LAPIC/IOAPIC/PIC, PTE encoding (`pte.h`), GRUB parsing, HAL inline/impl backends. Only arch code, the documented exemptions (`kernel/main.cpp`, `kernel/cmd.cpp`, `kernel/irq_balance.cpp`) and x86-only drivers may include these headers
- `src/cpp/arch/arm64/` — Linux-Image boot + PSCI SMP (`boot.S`), EL1 vectors, GICv3 + ITS, generic timer, PL011, FDT parser, PCIe ECAM, PTE encoding, HAL backends
- `src/cpp/kernel/` — scheduling, tasks, interrupt dispatch, SoftIrq, timers, timekeeping seam (`time.h`), locks (spinlock/mutex/seqlock/rwlock), panic/backtrace, dmesg ring buffer, the interactive shell (`cmd.cpp`), input layer (`input.cpp`), the ChaCha20 random pool every source feeds and everything reads from (`random.cpp`, `entropy.h`; see `docs/random.md`), the Rust FFI bridge (`rust_ffi.cpp`), symbol table
- `src/cpp/mm/` — 4-level page tables (`VirtToPhys` walk, `ProtectRange`), page allocator (fixed-size block allocator), pool allocator, VA allocator, `new`/`delete`
- `src/cpp/drivers/` — serial, console (`screen.cpp` picks EGA text on BIOS vs. the 8x16-font pixel framebuffer under UEFI), PIT/HPET/RTC, 8042 keyboard, PCI, MSI-X, ACPI. **No virtio and no USB**: both are Rust (`src/rust/virtio`, `src/rust/drivers/`)
- `src/cpp/lib/` — freestanding stdlib equivalents (`Stdlib::`), containers (list/vector/btree/ringbuffer/bitmap), CRC32, ChaCha20, formatting; some routines (`MemSet`/`MemCpy`/`StrLen`…) are in `arch/x86_64/stdlib_asm.asm` (portable C in `arch/arm64/stdlib_c.cpp`)
- `src/rust/` — a cargo workspace that compiles to a `#![no_std]` `staticlib` (`libkernel.a`) linked into the kernel:
  - `ffi/` (raw `extern "C"` declarations only) and `kcore/` (safe RAII wrappers around kernel services)
  - `block/` — **the whole block layer**: the device table every disk and partition is registered in (a driver registers as a `BlockDriver` trait object; a partition is an entry of the table itself, its I/O the disk's a few sectors on), the claims that keep two writers apart, the MBR and GPT readers, the `disks`/`partitions`/`diskread`/`diskwrite` commands and the kernel log written to a raw disk area (`disklog.rs`); the rest of the image reads and writes through `block::Disk` (`count`/`at`, `claim_as`)
  - `net/` — **the whole network layer**: the wire formats and the internet checksum (`wire.rs`), ARP, ICMP, UDP, TCP, the DHCP client, the DNS resolver, the HTTP client (plain TCP or TLS behind a transport seam), the shell over UDP, netconsole, the load target, the recycled frame pool every packet comes from, the devices themselves -- the `NetDriver` a NIC registers as, the queues between it and the stack, the UDP listeners, the receive dispatch, the per-CPU counters -- and the shell's network commands and `wget`
  - `fs/` — **the whole filesystem layer**: the VFS (mount table, path resolution, open handles, the file API — `Open/Read/Write/Seek`, `Stat`, `ReadDir`, `Rename`, `Truncate`) over the `FileSystem` trait each filesystem implements and the `vnode::Tree` arena each keeps its nodes in; **ext2 read-write** (the root, which `root=auto` mounts by the label `nos`), **nanofs** (on-disk, small, checksummed), **ramfs** and **procfs**; what boot mounts where (`rootfs.rs`), the shell's filesystem commands and the `fstest` self-test; another crate opens a file with `fs::vfs::Open::new(fs::vfs_instance()?, path, flags)`; see `docs/filesystems.md`
  - `virtio/` (the virtqueue and both virtio buses — virtio-pci modern and legacy, virtio-mmio v2) and `drivers/`: `virtio_blk`, `virtio_net`, `virtio_scsi`, `virtio_rng`, `nvme`, `usb` (the xHCI host controller and the HID boot keyboard on it, which on a UEFI laptop with no PS/2 is the only way in), `r8168`, `r8125`, `igb`
  - `tls/` — the TLS client (rustls + RustCrypto + webpki-roots, driven through rustls' unbuffered API — see `docs/tls.md`); `ssh/` — an SSH server's protocol, with no kernel in it (the `sshd` module serves it, see `docs/sshd.md`)
  - `kernel/` (entry points, the global allocator, the `sha256` command), `hello/` (self-test)
  - `kmod/` + `modules/` — **loadable modules**, Rust-only: each crate under `modules/` is built on its own (PIC, its own target dir) into a `.ko` shared object that `insmod` loads into a running kernel (`kernel/module.cpp`), binding it against an export table the Makefile generates from pass1.elf out of the `ffi` declarations; the boot self-test loads the embedded `modtest.ko` (see `docs/modules.md`)

There is no `src/cpp/{block,net,fs}` and no C++ view of any of those layers. A C++ file that needs one declares the `rust_*` / `kernel_*` calls it makes where it makes them: the tracer and the panic path into netconsole and the disk log, the idle path into the receive poll, boot into the frame pool, TCP, the services and the mounts, the C++ part of the shell into files.

Inside the image the crates call each other as crates -- a driver depends on `block` or `net`, `fs` on `block`, `net` on `fs` and `tls` (which takes its transport as a trait, being below `net`) -- and `kcore`'s `block`, `net`, `tcp` and `fs` modules are those layers *as a loadable module reaches them*: across the C ABI, the only seam something linked on its own can share with the kernel. A `kernel_*` name defined in Rust that no module imports and no C++ calls has no reason to exist.

The TLS crates are the only external dependencies in the tree, with two build-level constraints, both handled in `src/rust/.cargo/config.toml`. The RustCrypto crates are forced onto their software backends (`--cfg aes_force_soft`, `polyval_force_soft`, `poly1305_force_soft`, `chacha20_force_soft`, `curve25519_dalek_backend="serial"`; `sha2` by its `force-soft` feature in `kernel/Cargo.toml`): their runtime SSE2/AVX2 dispatch cannot be legalized for a target with SSE off, and the kernel keeps SSE off because it saves no XMM state on a context switch. And `getrandom` has no bare-metal backend, so `tls` registers the kernel entropy pool as its custom one. The sources are vendored in `src/rust/vendor` and the Makefile builds with `cargo --offline`, so no build touches the network; after changing a dependency -- or bumping the nightly pin, which changes what std itself resolves to -- run `scripts/vendor.sh` and commit what it produces.

## Conventions (critical)

This file is the authoritative copy of the project's rules; there is no other. They are how the goal at the top is kept in practice. First which language new code is in, then the non-obvious rules -- C++ first, and then what goes for both:

- **New code is Rust unless it has to be C++.** C++ is for the fundamentals that are C++ already, and for extending those in place: boot and arch bring-up, the MMU and the allocators, the scheduler and tasks, the locks, interrupt dispatch, timers, the HAL, the core of the shell, the module loader. Everything that sits on them is Rust: every driver (block, net, USB, virtio, anything on the PCI bus), every network protocol and service, every filesystem, the block layer, and the shell commands that belong to any of those -- a new command goes in the crate that owns the data (`igbdump` is in `drivers/igb`), not in `cmd.cpp`. Do not add a C++ view of a Rust layer or grow a C ABI so that new C++ can reach Rust: if new C++ would need one, the code is on the wrong side. When a C++ subsystem has to be reworked substantially anyway, moving it to Rust is the preferred direction. **What is optional is a loadable module** (`src/rust/modules/`, `docs/modules.md`): a server, a load generator, a diagnostic -- anything a machine can boot and run without -- is a `.ko` over `kcore`, as `sshd`, `netblk` and `blkload` are. The one thing a module cannot be today is a disk's or a NIC's driver: those register with their layer as trait objects from inside the image, and there is no C name for a module to bind.
- **Freestanding constraints**: no `std::` (use `Stdlib::` from `lib/stdlib.h`), no exceptions/RTTI, **no lambdas/closures**, no `thread_local`, no heap before `PageAllocatorImpl::Setup()`. `volatile` compound assignments are banned — write `x = x + y`.
- **Static constructors are unreliable.** Never initialize via a static instance constructor. Use the singleton + explicit init pattern: `static Foo& GetInstance(){ static Foo i; return i; }` plus a `bool Setup()` called once at boot. Heap-allocate non-trivial objects (e.g. `Mm::TAlloc<T, Tag>()`) rather than using static arrays of them.
- **Error handling**: return `bool`/pointer for pass-fail, `Stdlib::Error` (`lib/error.h`, carries code, file, line and function) for rich errors, `Stdlib::Result<T>` (`lib/result.h`) for value+error. Build with `MakeError(Stdlib::Error::NoMemory)` / `MakeSuccess()`; a `Result<T>` converts implicitly from a `T` and from an `Error`, so `return 42;` and `return MakeError(...);` are both all it takes. Always check return values. On error paths, release every resource acquired so far in reverse order. `BugOn(cond)` and `Panic("fmt", …)` for invariant violations.
- **OOM and `operator new`**: plain `new T(...)` **panics on OOM** and never returns `nullptr` — the compiler assumes the plain form is non-null, so a null check after it is dead code. Fallible allocations must use `new (Mm::NoThrow) T(...)` (the compiler keeps that null check; from `Stdlib::` code it is spelled `new (Kernel::Mm::NoThrow) T[...]`, as in `lib/vector.h`) or `Mm::TAlloc<T, Tag>()`, and check the result. See the comment in `mm/new.h` for why the plain form cannot be made nullable: a `noexcept` redeclaration does not compile, and the toolchain's clang parses `-fcheck-new` without implementing it.
- **Never allocate or free with a spinlock held.** `Mm::Free`/`Mm::Alloc` reach the page allocator, which shoots down the TLB on every other CPU (`CpuTable::InvalidateTlbRange` → IPI → `WaitGroup::Wait`) and waits for all of them to answer. A CPU spinning on the lock you hold has interrupts off and can never answer, so the two wait for each other forever -- no panic, nothing to reset the machine. Collect what needs releasing into a local list under the lock, unlock, then release. Better still, do not allocate on a datapath at all: net frames come from the frame pool, built once at boot and recycled through per-CPU caches over a lockless ring, and a driver hands a finished TX frame to `TxQueue::done` -- the only way out of `flush_tx` a frame has -- for the net layer to release off the lock. `CpuTable::SendTlbIPI` panics after ten seconds naming the CPUs that never answered, so a new instance of this bug is a report rather than a dead machine.
- **Memory refcounting** is explicit and easy to get wrong — `PageTable::MapPage(va, page)` does `+1`, `GetPage(phyAddr)` does `+1` (caller must `Put()`), `UnmapPage(va)` is net-0 (a `Get` and a `Put` inside) and returns the `Page*`. To fully undo a `MapPage`: `UnmapPage`, then `page->Put()`. To free a mapped page: `UnmapPage` + `FreePage` + `Put`. `FreePage` alone only puts the page back on the free list; it does not touch the refcount.
- **Never map DMA/device memory at `physAddr + KernelSpaceBase` directly.** Always go through `Mm::MapPages` / `Mm::AllocMapPages` so the `VaAllocator` (`mm/va_allocator.h`, a bitmap of free and used VA ranges, one per `FixedPageAllocator`) tracks the VA. What each pair in `mm/new.h` does:

  | Function | Allocates phys pages? | Maps at tracked VA? | Frees phys pages on unmap? |
  |---|---|---|---|
  | `Mm::Alloc` / `Free` | yes | yes (via slab) | yes |
  | `Mm::AllocMapPages` / `UnmapFreePages` | yes (contiguous) | yes | yes |
  | `Mm::MapPages` / `UnmapPages` | no (caller provides `physAddrs`) | yes | no (caller keeps ownership) |
- **The kernel image is W^X on both arches.** Late in boot `ProtectRange` splits it into text RX / rodata RO+NX / data RW+NX (`main.cpp`, `main_arm64.cpp`), and MMIO mappings are NX. Self-modifying code, executing from a heap buffer, or writing through a pointer into `.rodata` faults instead of silently working.
- **Memory barriers**: `Barrier()` is gone. Pick the semantic variant from `hal/barrier.h`: `Hal::SmpWmb/SmpRmb` (CPU↔CPU publish/consume, e.g. seqlock), `Hal::DmaWmb/DmaRmb` (CPU↔device rings/doorbells/OWN bits), `Hal::CompilerBarrier` (compiler-only). On x86 they all compile to a compiler barrier; on arm64 they become `dmb` — misclassification is invisible on x86 and bites on arm64. In Rust, device ordering uses `kcore::barrier::dma_wmb/dma_rmb` (`dmb oshst/oshld` on arm64) — `core::sync::atomic::fence` is NOT a substitute: it emits `dmb ish`, whose inner-shareable domain does not order against a PCIe master. Consuming device-written state needs a read barrier *after* the index/phase/OWN check and before the payload reads (an address-independent load pair is not ordered by a control dependency on arm64) — see `VirtQueue::GetUsed`, nvme `read_cqe`, r8168 `harvest`.
- **Write Rust with as little `unsafe` as the job allows, and put what is left in `kcore` and at the C ABI, not in the layers.** A new driver, protocol, filesystem or module should need none of its own beyond an `unsafe impl` saying a struct is plain words and the entry point C++ calls it by. Reach for the `kcore` type first (the list is in the Rust section); when the shape you need has none, add the type to `kcore` -- once, with the reason it is sound in its comment -- rather than an `unsafe` block at every use. Do not lower the count by hiding it: a pointer kept as a `usize`, a macro that folds ten blocks into one, a safe wrapper that trusts what it is given, all leave the risk and remove the warning. `scripts/unsafe-count.py [crate...]` counts the sites (blocks, `unsafe fn`, `unsafe impl`); a change that raises a layer's or a driver's number should be able to say why.
- **Arch discipline**: common code includes `hal/*` headers only. `Hal::` wrappers: `IsInterruptEnabled`, `IrqSave/IrqRestore` (not RFLAGS), `GetSp/SetSp/GetFp` (not GetRsp/GetRbp), `ReadCycleCounter` (not ReadTsc), `IrqEoi/SendIpi/GetCurrentCpuHwId` (not Lapic::), `TlbFlushPage/TlbFlushAll` (not Invlpg/CR3). Per-arch member functions (e.g. `CpuTable::StartAll`) live in arch TUs.
- **Style**: namespaces `Kernel::`, `Kernel::Mm::`, `Stdlib::`. Trace with `Trace(level, "fmt", …)` / Rust `trace!(...)`; level 0 is always visible and the per-subsystem level constants (`KbdLL`, `UsbLL`, `PageAllocatorLL`, …) are at the top of `kernel/trace.h`. To debug a subsystem raise one there, or raise the global level with the `loglevel N` shell command or the `loglevel=N` boot parameter -- no rebuild, which is what you want on a box whose only console is a UDP socket. No magic numbers: name constants (`static const`, `constexpr` or an `enum`, in the header or class they belong to). `/* ... */` for a multi-line comment, `//` for a one-line one; `auto` is fine for a deduced local, and the smart pointers in `lib/` are there to be used. Preserve existing formatting; don't reflow unchanged code. 4-space indent.
- **C++ gets a second pass for undefined behaviour before it is done.** Once it is written and builds, re-read the diff looking for nothing else: `-Wall -Wextra -Werror` and cppcheck catch little of it, and in a kernel UB is not a crash at the faulty line but a machine that wedges somewhere else, on one architecture, at one optimisation level. What to look for, most of it from bugs this tree has had: a value from outside -- a device register, a packet, a disk, the Rust side, the shell -- used as an index, a length, a shift count or a handle before it is range-checked (`1 << n` with `n` from hardware, `count * size` that can wrap, a PCI slot shifted into an address unmasked); signed overflow and conversions that truncate; a read of anything not yet initialised, padding copied out and members a constructor skips included; a `reinterpret_cast` onto bytes that may be misaligned or are another type's (wire and on-disk structures go through `MemCpy` or byte accessors); a pointer or reference that outlives what it points at -- a stack object handed to a callback, a list entry freed while still linked, an object freed while an interrupt handler or another CPU may still hold it; shared state touched from two CPUs or from an interrupt without the lock, the atomic or the barrier that orders it, and `volatile` standing in for any of those; a null check after plain `new`, or none after a fallible allocation; a static object with a constructor; control falling off the end of a non-void function. Say in the change what was checked and what was found.
- The C++ build uses `-Wall -Wextra -Werror`, so warnings break the build.

## Rust: the layers, `kcore`, and writing a driver

**Adding a kernel service to Rust is three steps**, and a module gets it by the same three (the export table is generated from the `ffi` declarations):

1. the C++ function in `src/cpp/kernel/rust_ffi.cpp`;
2. its raw declaration in `src/rust/ffi/src/<module>.rs` (+ `pub mod` in `ffi/src/lib.rs`);
3. the safe wrapper in `src/rust/kcore/src/<module>.rs` (+ `pub mod` in `kcore/src/lib.rs`).

- **`ffi/`** holds `extern "C"` declarations and `#[repr(C)]` structs and no logic. Every pointer is raw (`*mut u8`, `*const u8`): no reference crosses the boundary. A kernel object is an opaque `usize` handle, 0 for null or failure. The blocks are `unsafe extern "C" { .. }` -- at the start of a line, which is what the Makefile's module export table looks for -- and a function that is sound for *any* argument at *any* time is declared `pub safe fn`, so that calling it needs no `unsafe` block and the blocks that are left mean something. Check the definition before writing `safe`: a C++ one that takes plain values and validates them (soft IRQ types are range-checked; PCI config reads are *not* safe, the arm64 ECAM accessor does not bound the slot or the function), or a Rust export that is itself a safe `extern "C" fn` and only looks its handle up in a table. Anything with a buffer, a callback or a C++ handle stays unsafe, and so do `irq_restore` and `preempt_enable`, which can open a window inside somebody else's critical section.
- **`kcore/`** is where a handle becomes a type. Whatever needs cleanup implements `Drop` calling the matching `kernel_*_destroy` / `kernel_*_stop` / `kernel_*_put`; a handle that must not be `Send`/`Sync` carries `PhantomData<*const ()>`; ownership crosses to C++ by value, inside the wrapper, so no call site has a `forget` to remember.
- **`rust_ffi.cpp`**, the C++ side: all of it lives in that one file. Register/create functions heap-allocate their adapters with `Mm::TAlloc<T, RustAllocTag>()`, never a static array of non-trivial objects. The slot pools for IRQ, timer and MSI-X callbacks are under a `RawRwSpinLock`: read-locked in the handlers, write-locked with interrupts saved to register or unregister. Handles are raw pointers cast to `unsigned long`, 0 for failure.

### The shapes that used to need `unsafe`, and the type each has now

Look here before writing an `unsafe` block: the reason each is sound is in the type's own comment.

- **A lock owns its data** (`kcore::sync`: `Mutex<T>`, `SpinLock<T>` and the rest, in the table below) -- never a bare lock beside an `UnsafeCell`. A lock that guards nothing is `Lock<()>`. Guards are values: hold two, drop them in either order, return one from a function (`Tcp::take_fresh`).
- **What waits when dropped** -- a `UdpListener` (for the receive path), a `TaskHandle` (for the task), an interrupt handle -- sits in its own `Lock<Option<..>>`: `take()` it under the lock, drop it after. Dropped under the lock its wait needs, it is a deadlock.
- **The one of something** is a `Once`/`OnceBox` static, not an `AtomicPtr` and a `&*ptr`.
- **Per-CPU state** is `PerCpu<LocalCounter…>` for numbers and `CpuLocal<T>` for anything exclusive -- never an `UnsafeCell<[T; MAX_CPUS]>` indexed by `cpu::id()`, which is a data race the moment a task migrates between the index and the access.
- **What only the receive path touches** is an `RxOwned<T>`, reached with the `&mut RxContext` the receive pass makes once and lends down (`net::nic`, where a service's `UdpHandler` is lent each frame as a `Lent` and gathers its replies in a `TxBatch`).
- **An on-disk or on-wire structure** goes through `kcore::pod`, not a cast onto the bytes.
- **A handle from outside is looked up, not dereferenced**: a net device, a TCP connection, a block device and an open file are each a slot of a table that lives as long as the kernel (`DEVICES.by_handle`, `TCP.by_handle`, block `device()`, `vfs::Handle`), so a word that is not one is `None` rather than undefined behaviour, and the functions taking them need not be `unsafe`.
- **A graph is an arena and ids**, not raw pointers: `fs::vnode::Tree` hands out `NodeId`s -- a slot and a generation -- so a stale one finds nothing.
- **A seam between two pieces of Rust is a trait** or a `&mut dyn` (`vfs::FileSystem`, `http::Sink`, `UdpHandler`, `tls::Transport`, `BlockDriver`, `NetDriver`), not an `extern "C" fn(ctx: *mut u8, …)` table: the C ABI is for what C++ or a separately linked module is on the other side of. An export that trusts a pointer is `unsafe extern "C" fn` with a `# Safety` section; one that takes only validated handles and plain values is a safe `extern "C" fn`; **an export nobody calls is deleted**, not kept for symmetry.
- **A callback is a function item over its target**: `register_for(.., target: &'static T, handler)`, the handler an `fn(&'static T)` named directly (`Nic::interrupt`), never a closure that captures. `kcore` checks at compile time that it has no bytes and stamps out the trampoline per handler type, so the context word *is* the target (`kcore/src/callback.rs`).
- **Device memory is cells, not `read_volatile` through a cast pointer**: a descriptor is a `#[repr(C)]` struct of `Volatile<u32>` (`unsafe impl Descriptor` says so once), a ring is `DmaBuffer::leak_ring`'s `&'static [D]` -- shared by the device, the poll and the state dump, which reads it live -- and anything else in a `DmaBuffer` crosses through `load`/`store`/`bytes`. The barriers stay where they were (the barrier rule in Conventions).

### Writing a driver

The traits' own comments (`block/src/table.rs`, `net/src/device.rs`, `kcore/src/entropy.rs`) are the contract; the smallest real one of each kind is the example: `drivers/virtio_blk` (block; `drivers/nvme` for the asynchronous path), `drivers/r8168` (a NIC), `drivers/virtio_rng` (an entropy source, the one kind that still goes through a `kcore` trampoline, because the pool is C++).

- **The device lives for good.** It is `Box::leak`ed, so it is `&'static`: what the interrupt is pointed at and what the layer's table keeps, as a trait object -- no ops table, no `ctx`. Shutdown is `quiesce(&self)`, not a `Drop`: the register writes that stop the hardware, then the interrupt handles. Nothing is freed -- the device, its rings and its BAR mapping stay, because the tables that point at them do.
- **Interrupts**: `MsixInterrupt::register_for(&table, index, dev, Dev::interrupt)` (slots shared by every Rust driver) or `LegacyInterrupt::register_level_for(pci_dev, dev, Dev::interrupt)` (the line may be shared, so the handler says by its own status register whether the interrupt was its). The handler runs in IRQ context -- no sleeping, no allocating -- and may run on two CPUs at once when its vector moves, so of the device it touches registers, atomics and IRQ-safe locks. The handle unregisters on drop: keep it in a lock inside the device, and have `quiesce` take it out and drop it after the lock.
- **A block driver** depends on the `block` crate, implements `block::BlockDriver` and calls `block::register_driver(name, dev)`. Calls arrive from any task on any CPU, several at once: what one needs exclusively sits behind a lock in the device. A buffer is whole sectors and never empty, and the device may DMA straight into it. `fn is_async(&self) -> bool { true }` adds `submit`/`kick`.
- **A NIC** depends on the `net` crate and implements `net::NetDriver` with its rings as `type Tx` / `type Rx`. The rings stay the init function's until `net::register(name, mac, dev, tx_ring, rx_ring)` hands them over, which comes last, because from there on the driver is called. The transmit ring then lives *inside* the device's transmit lock, next to the queue it drains, and the receive ring behind the receive pass's `RxContext`: `flush_tx` and `process_rx` are lent them as `&mut`, nothing else can reach them, and the interrupt handler gets registers and atomics and no more. A frame from `TxQueue::dequeue()` holds the DMA buffer the hardware is about to read: keep it in the ring's `Vec<Option<Frame>>` shadow until the hardware is done, then hand it to `stack.done(frame)` -- never drop it there (the spinlock rule above). On receive, `Frame::alloc_rx(max)` gives a frame of `len() == 0`; post its `data_phys()`, and once the hardware has filled it `set_len(received)` and hand it up with `RxQueue::enqueue`, or gather a `FrameQueue` and `deliver` it under one lock. What a state dump needs of a ring the poll publishes in atomics. If `register` refuses, it leaks the rings rather than dropping them -- the hardware is running on them -- and the driver quiesces.
